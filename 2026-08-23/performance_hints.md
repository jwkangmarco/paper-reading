## 1. Background — "성능은 나중에"가 틀리는 이유

**Knuth의 문장은 늘 잘려서 인용된다.** 전문은 이렇다.

> "We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. **Yet we should not pass up our opportunities in that critical 3%.**"

**저자들은 오히려 다른 Knuth 인용을 앞세운다 — 12% 개선을 하찮게 보는 통념에 대한 반박이다.** Knuth는 12% 속도 개선을 두고 "많은 사람이 무의미하다고 선언할 것"이라며 이렇게 잇는다: 효율을 무시하라는 오늘날의 통념은 "최적화한답시고 디버그도 유지보수도 못 하는 프로그램을 만드는 소탐대실형 프로그래머들"에 대한 과잉 반응일 뿐이고, **"확립된 공학 분야에서 쉽게 얻을 수 있는 12% 개선은 결코 사소하다고 여겨지지 않는다. 소프트웨어 공학에서도 같은 관점이 지배해야 한다."** 물론 일회성 작업이라면 그런 최적화를 하지 않겠지만, 품질 있는 프로그램을 준비하는 문제라면 그런 효율을 거부하는 도구에 스스로를 가두고 싶지 않다는 것.

**"일단 단순하게 짜고 나중에 프로파일링해서 고치자"는 접근이 실패하는 지점은 네 가지다.**

| # | 실패 양상 | 왜 문제인가 |
|---|---|---|
| 1 | **프로파일이 평평해진다(flat profile)** | 큰 시스템 전체에서 성능이 조금씩 새면 뚜렷한 hotspot이 없다. **어디서 시작할지조차 알 수 없다** |
| 2 | **고칠 사람과 겪는 사람이 다르다** | 라이브러리라면 성능 문제를 겪는 쪽은 남(다른 팀)의 코드를 읽고, 그 팀과 최적화의 중요성을 협상해야 하는 사람이다 |
| 3 | **이미 쓰이는 시스템은 바꾸기 어렵다** | 사용량이 많아진 뒤에는 큰 변경 자체가 불가능해진다 |
| 4 | **비싼 우회로로 덮게 된다** | 쉽게 고칠 수 있는 문제인지 판별이 안 되니, 과도한 replication이나 심한 overprovisioning으로 때우게 된다 |

**그래서 저자들의 처방은 온건하다** — "코드를 쓸 때, **가독성·복잡도를 크게 해치지 않는다면 더 빠른 쪽을 고르라**." 전면적 최적화 지시가 아니라 **기본값 선택의 문제**로 프레이밍한다.

**어떤 코드냐에 따라 고민의 깊이가 다르다** (원문의 3분류 — 코드를 쓰는 시점의 트리아지):

- **테스트 코드**: 알고리즘·자료구조의 점근 복잡도만 신경 쓰면 된다. (단, 개발 사이클도 성능이다 — 오래 걸리는 테스트를 쓰지 마라.)
- **애플리케이션 전용 코드**: 이 코드에 성능이 얼마나 중요한지 파악하라. 보통 어렵지 않다 — **초기화/설정 코드인지, hot path(서비스의 매 요청 처리 등)에 놓일 코드인지**만 구분해도 충분할 때가 많다.
- **여러 앱이 쓸 라이브러리 코드**: 얼마나 민감해질지 미리 알 수 없다. **여기가 이 문서의 단순 기법들이 특히 중요한 지점이다.** 예컨대 보통 원소가 적은 벡터라면 `std::vector` 대신 `absl::InlinedVector`를 쓰는 것 — 어렵지 않고 비지역적 복잡도를 더하지 않는데, 나중에 이 코드가 큰 자원을 쓰게 되면 처음부터 빠르고, 프로파일에서 다음 타깃을 찾기도 쉬워진다.

## 2. Motivation

### 핵심 통찰 1: 측정하기 전에 추정할 수 있어야 한다

**프로파일링은 코드가 있어야 가능한데, 설계 시점에는 코드가 없다.** 그래서 저자들은 **back-of-the-envelope 계산**을 앞세운다. 구현 없이도 대안들의 대략적 성능을 빠르게 어림해서, 일부 대안을 **구현해 보기 전에 걸러내는** 것이 목적이다. 절차는 셋이다.

```
① 저수준 연산이 몇 번 일어나는지 센다 (disk seek 수, network round-trip 수, 전송 바이트 수 …)
② 각 연산의 대략적 비용을 곱한다
③ 더한다  →  자원 사용량(resource usage)

* latency가 궁금하고 시스템에 동시성이 있다면, 겹치는 비용을 고려해 조금 더 계산해야 한다
  (자원 사용량과 latency는 다른 양이다 — 아래 예제 B가 이 구분의 시범)
```

**연산별 대략 비용** (2007년 Stanford 강연 표의 갱신판 — 2011년 관련 강연 영상만 현존):

```
L1 cache reference                             0.5 ns
L2 cache reference                             3 ns
Branch mispredict                              5 ns
Mutex lock/unlock (uncontended)               15 ns
Main memory reference                         50 ns
Compress 1K bytes with Snappy              1,000 ns
Read 4KB from SSD                         20,000 ns
Round trip within same datacenter         50,000 ns
Read 1MB sequentially from memory         64,000 ns
Read 1MB over 100 Gbps network           100,000 ns
Read 1MB from SSD                      1,000,000 ns
Disk seek                              5,000,000 ns
Read 1MB sequentially from disk       10,000,000 ns
Send packet CA->Netherlands->CA      150,000,000 ns
```

> **저수준 표만으로는 부족하다.** 저자들은 **자기 시스템의 상위 연산 비용**도 함께 추적하라고 말한다 — SQL point read 한 번, Cloud 서비스 왕복 한 번, 단순 HTML 한 장 렌더링의 대략 비용. *"If you don't know the relevant cost of different operations, you can't do decent back-of-the-envelope calculations!"*

#### 예제 A: 40억 바이트(10억 개 × 4B) quicksort

좋은 quicksort는 크기 N 배열을 log(N)번 훑는다. 매 pass마다 배열이 메모리에서 캐시로 스트리밍되고, partition 코드가 원소마다 피벗과 한 번씩 비교한다. 지배 비용을 더해 보면:

```
메모리 대역폭 : 배열 4GB, 코어당 대역폭 ~16GB/s 가정 → pass당 0.25s × ~30 passes = ~7.5s
분기 예측실패 : 비교 N·log(N) = ~300억 회, 그 절반이 실패라 가정 (맞춘 분기는 공짜로 취급)
               150억 × 5ns                                        = 75s
                                                             합계 ≈ 82.5s
```

> **지배 항이 메모리가 아니라 분기 예측 실패다.** 원문은 여기서 캐시 보정을 한 번 더 시범한다 — 32MB L3는 2²³개 숫자를 담으므로 마지막 22 pass는 L3 안에서 돌고, 메모리 전송은 7.5s → **2.5s**(4GB 전송 10회)로 준다. 그러나 75s 앞에서는 의미가 없으므로 이 보정은 "필요 없었다"고 스스로 평가한다. **추정의 값어치는 정밀도가 아니라 "무엇이 지배하는지"를 먼저 알려주는 데 있다.**

#### 예제 B: 썸네일 30장짜리 웹페이지 (원본 이미지 ~1MB, 디스크 저장)

| 설계 | 계산 | 결과 |
|---|---|---|
| 디스크에서 **순차** 읽기 | (seek 5ms + 전송 10ms) × 30장 | **450 ms** |
| **K개 디스크에 분산**해 병렬 읽기 | 자원 사용량은 같고 latency만 ~1/K (운 나쁘면 한 디스크에 몰리는 분산은 무시) | 디스크 수백 개면 **~15 ms** |
| 전부 **단일 SSD**에 | (20µs + 1ms) × 30장 | **~30 ms** |

> 자원 사용량과 latency를 분리해 계산하는 시범이다. 병렬화는 **자원을 줄이지 않고 latency만** 줄인다.

### 핵심 통찰 2: 측정 — 도구, 그리고 프로파일이 평평할 때

**측정 역량은 성능 작업의 1번 무기다.** 첫 도구는 pprof(로컬·프로덕션 모두 쉬움), 더 깊이 보려면 perf. 원문의 프로파일링 팁 다섯:

- 프로덕션 바이너리를 **적절한 디버깅 정보 + 최적화 플래그**로 빌드하라.
- 가능하면 개선 대상 코드를 덮는 **마이크로벤치마크**를 써라 — 개선의 턴어라운드를 줄이고, 효과를 검증하고, 미래의 회귀를 막는다. 단, 전체 시스템 성능을 대표하지 못하는 함정이 있다.
- 벤치마크 라이브러리가 **하드웨어 성능 카운터** 읽기를 함께 출력하게 하라 — 정밀도와 통찰 둘 다 좋아진다.
- **락 경합은 CPU 사용률을 인위적으로 낮춰 보이게 한다**(락 대기는 CPU를 안 쓰므로 프로파일에서 안 보인다). 일부 mutex 구현은 경합 프로파일링을 지원한다.
- ML 성능 작업에는 ML 전용 프로파일러를 써라.

> **프로파일링은 성능 작업만을 위한 게 아니다.** 저자들은 **낯선 코드베이스를 파악하는 수단**으로도 프로파일링을 권한다 — 동적 콜그래프에서 비중 높은 루틴의 소스를 읽으면 "이 프로그램이 실제로 무엇을 하는가"의 감이 잡히고, 그 감이 낯선 코드를 고칠 자신감이 된다.

**저수확 과일을 다 딴 뒤에는 CPU 프로파일에 뚜렷한 봉우리가 없다(flat profile).** 이때의 대응 여섯 가지:

| 대응 | 내용 |
|---|---|
| **작은 개선을 무시하지 말 것** | 한 서브시스템에서 1% 개선 20개는 충분히 가능하고 합치면 상당한 폭이다. 전제는 **안정적이고 품질 좋은 마이크로벤치마크** (§5.3의 복합 CL들이 이 유형의 실물) |
| **콜스택 위쪽의 루프를 찾을 것** | flame graph가 유용. 루프나 그 안에서 불리는 코드의 구조 자체를 재편할 여지를 본다. 원문 사례 — 노드·엣지를 하나씩 넣으며 그래프를 점진 구축하던 코드를 입력 전체를 한 번에 넘기는 방식으로 바꿔, 엣지당 반복되던 내부 검사를 제거 |
| **한 걸음 물러나 구조를 볼 것** | 미시 최적화 대신 콜스택 상단의 구조 변경. §4.2 알고리즘 개선 기법이 여기 해당 |
| **지나치게 일반적인 코드를 찾을 것** | 단순 prefix 매칭이면 되는 곳에 정규식을 반복 실행하고 있지 않은지 — 맞춤/저수준 구현으로 교체 |
| **할당 프로파일을 볼 것** | 할당 최다 기여자부터 깎는다. 효과 둘: ① 할당기(GC 언어면 GC) 시간 자체가 줄고 ② **tcmalloc 장기 실행 프로그램에서는 할당마다 다른 캐시라인으로 가는 경향이 있어 cache miss도 함께 준다** |
| **하드웨어 카운터 프로파일** | cache miss율이 높은 함수를 짚어준다 |

## 3. Contributions

1. **추정 우선의 성능 문화**: 측정 이전에 back-of-the-envelope으로 대안을 걸러내는 절차와, 그에 필요한 연산 비용표 제공.
2. **기법 카탈로그**: API 설계 · 알고리즘 · 메모리 표현 · 할당 · 불필요한 일 제거 · 컴파일러 협조 · 통계/로깅 · 코드 크기 · 병렬화 · protobuf · C++ 타입 · bulk 연산의 12개 축.
3. **모든 기법에 실제 CL과 벤치마크를 붙임**: 주장마다 Google 내부의 실제 변경과 수치가 근거로 달려 있다. 원칙 나열에 그치지 않는다.
4. **평평한 프로파일 대응법 + 복합 CL 사례집**: 대부분의 성능 문서가 다루지 않는, "쉬운 것을 다 한 뒤"의 전략과 그 실물 사례들.

## 4. Method — 기법 카탈로그

### 4.1 API 설계

**전제: 성능 개선은 캡슐화 경계 안에서 끝나도록 코드를 조직하라.** 아래 기법 중 일부는 자료구조와 함수 시그니처를 바꿔야 해서 호출자에게 파괴적일 수 있다. 모듈이 **deep**할수록(좁은 인터페이스 뒤에 많은 기능) 공개 인터페이스를 건드리지 않고 내부에서 최적화를 끝내기 쉽다.

> ⚠️ **기능 추가 압력을 경계하라.** 널리 쓰이는 API에는 기능을 더하라는 압력이 심한데, 새 기능은 미래의 구현을 제약하고 **그 기능이 필요 없는 사용자에게까지 비용을 물린다.** 예 — C++ 표준 라이브러리 컨테이너 상당수가 **iterator 안정성**을 약속하는데, 이 때문에 일반적 구현에서 할당 횟수가 크게 늘어난다. 정작 대다수 사용자는 포인터 안정성이 필요 없다.

**Bulk API — 경계 넘기 비용을 상각하고, 때로 알고리즘적 이득까지 얻는다.** 사례 셋:

- `MemoryManager::LookupMany`: 텐서 여러 개를 한 호출로 조회. **부수 효과로 시그니처도 단순해졌다** — bulk 버전을 만들며 보니 클라이언트가 알아야 할 것은 "전부 찾았는가"뿐이어서 `Status` 대신 `bool` 반환으로 줄었다.
- `ObjectStore::DeleteRefs`: 참조 여러 개를 **락 한 번**으로 삭제 (호출자 루프의 ref당 락 획득을 상각).
- **Floyd's heap construction**: 힙에 원소를 하나씩 넣으며 매번 힙 속성을 복구하면 O(N log N), 전체를 한 번에 bulk 초기화하면 **O(N)** — bulk API가 알고리즘적 이득으로 이어지는 예.

**호출자를 못 바꿀 때는 내부에서 bulk로 처리하고 캐시하라.** 렉시콘 사례 — 조회 한 번에 K개 엔트리 블록 전체를 디코드해야 하는 구조였는데, 디코드 결과를 캐시에 담아 두고 이후의 단건 조회들이 캐시를 먼저 보게 했다.

**View 타입을 인자로 받아라.** `std::string_view`, `absl::Span<T>`, `absl::FunctionRef<R(Args...)>` — (소유권 이전이 아닌 한) 복사를 없애고, **호출자가 자기 컨테이너 타입을 자유롭게 고르게 한다**(한 호출자는 `std::vector`, 다른 호출자는 `InlinedVector`).

**미리 할당·계산된 인자를 받게 하라.** 자주 불리는 루틴이라면, 호출자가 이미 가진 정보나 소유한 버퍼를 넘겨받아 내부의 임시 할당·재계산을 없앤다. 사례 — `RPC_Stats::RecordRPC`에 호출자가 이미 갖고 있던 `WallTime`을 넘기는 변형을 추가 (내부의 `WallTime_Now()` 재호출 제거).

**Thread-compatible(외부 동기화) > Thread-safe(내부 동기화)를 기본으로.** 일반적 용도의 타입은 thread-compatible로 두어 **동기화가 필요 없는 호출자가 그 비용을 물지 않게** 하라. 사례 — 호출자가 이미 동기화되어 있던 클래스에서 `MonitoredMutexLock`을 걷어내자 getter가 한 줄 반환문이 됐다. **단, 반대 방향의 단서도 있다**: 타입의 전형적 사용이 동기화를 필요로 한다면 동기화를 타입 안으로 넣어라 — 그래야 호출자에 영향 없이 동기화 메커니즘을 (샤딩 등으로) 개선할 수 있다.

### 4.2 알고리즘 개선

**가장 결정적인 기회는 알고리즘에서 온다 — O(N²)→O(N lg N)→O(N), 지수적 동작 회피.** 안정된 코드에서는 드물지만, 새 코드를 쓸 때 주의를 기울일 값어치가 있다.

**사례 1 — 사이클 탐지를 reverse post-order 일괄 투입으로.** 노드·엣지를 하나씩 추가하며 엣지당 비싼 작업을 하던 것을, DFS가 남기는 역위상 순서로 rank를 매기며 **그래프 전체를 한 번에** 투입 — 엣지 추가 시 `rank[src] >= rank[dst]` 비교만으로 사이클 탐지가 자명해진다. 호출부(`MergeGraph::Init`)도 `InitFrom` 한 줄로 단순해졌다.

**사례 2 — mutex 데드락 탐지 알고리즘 교체: ~50배 + 스케일 한계 제거.** Pearce & Kelly의 동적 위상정렬 알고리즘(JEA 2006) 기반으로 재작성. 공간이 O(|V|²) 비트 → **O(|V|+|E|)** (락 획득 순서 그래프는 매우 성기다), 핵심 코드는 ~100줄. 구 알고리즘은 성능 절벽을 피하려고 **2K개 제한**을 걸어 두었는데, 새 알고리즘은 수백만 mutex까지 문제없이 스케일해서 이 인위적 제한을 풀 수 있었고 — **그 결과 실제 프로그램들에 잠복해 있던 데드락 여러 개가 드러났다** (성능 개선이 정확성 개선을 부른 사례). 벤치마크(DEBUG 모드): 2k 노드에서 InsertEdge당 22µs → **0.5µs**, 구 알고리즘은 16k에서 무너지지만 새것은 1M 노드에서도 534ns.

**사례 3 — 자료구조가 "맞아 보여서" 쓴 것을 의심하라.** `IntervalMap`(O(lg N) 조회)은 인접 블록 병합을 지원하는 "맞는" 자료구조로 보여 선택됐지만, 인접 블록은 해시 조회로도 찾을 수 있다(이전 블록 길이를 엔트리에 저장). `flat_hash_map`(O(1))으로 바꿔 (CL의 다른 변경 포함) `tpu::BestFitAllocator` **~4배**.

**사례 4 — 정렬 교집합 → 해시 조회.** 두 노드가 공통 소스를 공유하는지를 "각 노드의 소스를 정렬해 받아 sorted intersection"(O(N log N))하던 것을, 한쪽을 해시테이블에 넣고 다른 쪽을 순회(O(N))로. 대형 컴파일 벤치마크 28.5s → 22.4s (**-21.6%**).

**사례 5 — 해시 함수 품질도 알고리즘이다.** `Location` 객체의 해시가 `address()` 필드 하나만 쓰고 있어 충돌이 잦았다(사실상 O(N) 동작). 주요 필드를 모두 섞는 제대로 된 해시(`MurmurCat`)를 구현해 O(1)을 회복.

### 4.3 메모리 표현

**목표는 흔한 연산이 만지는 캐시라인 수를 줄이는 것이다.** 그러면 ① 비싼 cache miss를 피하고 ② **메모리 버스 트래픽이 줄어 같은 기계의 다른 프로그램까지 빨라진다.**

**Memory layout — 큰 메모리/캐시 풋프린트를 가진 타입은 배치를 설계하라.** 원문의 체크리스트:

- 정렬(alignment) 요구가 다른 필드 사이의 **패딩을 줄이도록 필드 재배치**
- 들어갈 값이 작으면 **더 작은 숫자 타입** (enum도 조심 — `enum class OpType : uint8_t`처럼 명시하지 않으면 워드 하나를 통째로 차지할 수 있다)
- **함께 접근되는 필드를 가까이** — 흔한 연산이 만지는 캐시라인 수가 준다
- **hot 읽기전용 필드를 hot 가변 필드와 분리** — 가변 필드에 쓸 때마다 읽기전용 필드가 근처 코어 캐시에서 쫓겨나는 것을 방지
- **cold 데이터를 hot 옆에서 치우기** — 구조체 끝으로, 간접 참조 뒤로, 또는 별도 배열로
- 비트/바이트 인코딩 압축은 **잘 테스트된 모듈 안에 캡슐화되고 절감이 클 때만** — under-alignment, 접근 코드 비대화 같은 부작용을 벤치마크로 검증하라

**포인터 대신 인덱스.** 64bit 머신에서 포인터는 8바이트다. 포인터가 많은 자료구조는 `T*` 간접 참조로 메모리를 잔뜩 먹는다. `T[]`에 대한 32bit 인덱스로 바꾸면 참조 자체가 작아지고, **원소 저장이 연속적이라 지역성도 좋아진다.**

**Batched storage — 원소마다 객체를 할당하는 컨테이너를 피하라.** `std::map`·`std::unordered_map`은 원소당 별도 할당 → `std::vector`·`absl::flat_hash_map`처럼 청크/플랫 표현을 쓰는 타입으로. 캐시 동작이 훨씬 좋고 할당기 오버헤드도 적다. 원소들을 고정 크기 청크로 나누는 기법은 **점근 성능을 유지한 채** 캐시 풋프린트를 크게 줄인다.

**Inlined storage.** 원소가 보통 적은 컨테이너는 상위 레벨에 소수 원소 공간을 내장한 타입(`absl::InlinedVector` 등)으로 — 스택 변수로 자주 생성되거나 동시에 많이 살아 있을 때 할당을 아예 없앤다. ⚠️ `sizeof(T)`가 크면 내장 backing store도 커지므로 부적합할 수 있다.

**중첩 맵 평탄화 — 단, 방향은 키 크기가 정한다.** `btree<a, btree<b,c>>` → `btree<pair<a,b>, c>`로 바꾸면 할당과 캐시 풋프린트가 준다(문자열 키였던 사례는 `string_view` 쌍 + 값 포인터로). **그러나 첫 키가 크면 반대로 가야 한다** — (문자열 경로 + 숫자 서브키)를 단일 해시테이블에 넣었던 코드를 **경로로 1단계 / 서브키로 2단계**로 쪼갰더니 마이크로벤치마크 **+76%**: 경로 하나당 평균 1,000개 키가 붙어 있어 **경로 문자열 저장이 1/1000로** 줄었고, 같은 경로의 서브키들을 몰아 접근하는 패턴도 빨라졌다.

**Arena.** 할당 비용 절감에 더해, **독립적으로 할당된 객체들을 물리적으로 인접 배치**하고 소멸 비용 대부분을 없앤다. 서브객체 많은 복합 자료구조에 가장 효과적이며, 초기 크기를 적절히 주면 더 좋다. ⚠️ 수명 짧은 객체를 수명 긴 arena에 넣으면 메모리만 붓는다.

**맵 대신 배열.** 키 도메인이 작은 정수/enum이거나 원소가 매우 적으면 배열로 — 사례: `flat_map<int,int>` → `int map[128]` (RTP payload type → clock frequency).

**집합 대신 비트벡터.** 도메인이 작은 정수면 `InlinedBitVector` — 합집합=OR, 교집합=AND로 집합 연산까지 효율적. Spanner 배치 시스템에서 `dense_hash_set<ZoneId>` → `InlinedBitVector<256>`:

```
BM_Evaluate/1      960 →  676   +29.6%
BM_Evaluate/5     3780 → 2665   +29.5%
BM_Evaluate/20   17922 → 12338  +31.2%
BM_Evaluate/40   36836 → 26430  +28.2%
```

같은 계열로, XLA에서 명령어 간 도달성(reachability)을 `unordered_map<HloInstruction*, unordered_set<...>>` 대신 **조밀 id 부여 + 비트 행렬**로 표현한 사례도 있다.

### 4.4 할당 줄이기

**할당의 비용은 셋이다**: ① 할당기에서 보내는 시간 ② 새 객체의 (때로 비싼) 초기화와 소멸 ③ **할당마다 새 캐시라인에 놓이는 경향** — 많은 독립 할당에 흩어진 데이터는 캐시 풋프린트가 커진다. (GC 런타임은 연속 할당을 인접 배치해 ③을 다소 완화하기도 한다.)

**불필요한 할당 자체를 제거하라.** 사례 둘 — ① `LiveTensor` 생성자가 `dinfo`가 비었을 때마다 `make_shared<DeviceInfo>()`를 새로 만들던 것을 **정적 싱글턴 공유**로 (벤치마크 처리량 +21%의 일부) ② 벡터를 할당해 0으로 채우던 것을 **정적 0 배열**로 대체하되, 드물게 큰 폭이 필요하면 그때만 할당하는 fast/slow 구조로. 또한 수명이 스코프에 갇힌 객체는 힙 대신 **스택 할당**을 (큰 객체의 스택 프레임 크기는 주의).

**resize / reserve로 미리 크기를 잡아라.** 최대(또는 예상 최대) 크기를 알면 backing store를 미리 확보 — N번의 `push_back` 대신 `resize(ndocs)` 후 포인터로 채우기. ⚠️ 단서 둘: **한 원소씩 자라며 resize/reserve를 부르면 이차(quadratic) 동작**이 될 수 있다. 그리고 원소 생성이 비싸면 `resize`(생성자 호출 2배) 대신 **`reserve` + `push_back`/`emplace_back`**.

**복사를 피하라.** 이동(move)을 선호하고 — 사례: 400KB 텐서를 gRPC로 받을 때 복사 한 번 제거 = **10~15%**, 큰 옵션 구조체 `Create(opts)` → `Create(std::move(opts))` — 수명이 허락하면 임시 자료구조에는 **객체 복사 대신 포인터/인덱스**를 담아라(들어온 proto 리스트에서 고르는 로컬 맵은 proto 복사가 아니라 포인터를; 큰 객체 벡터의 정렬은 인덱스 벡터 정렬로). 부수 사례: `std::stable_sort`는 내부 복사가 있다 — 동률 순서를 비교자에 넣을 수 있으면 `std::sort`로.

**임시 객체를 재사용하라.** 루프 안에 선언된 컨테이너/객체는 매 반복 생성·소멸·리사이즈된다. 선언을 루프 밖으로 끌어올리면 재사용된다 — **컴파일러는 언어 의미론상 이 호이스팅을 대신 못 해 주는 경우가 많다.** 사례: 루프 밖 `T profile;` 재사용(sstable 순회), 루프 밖 `ResourceRecord record;` + `record.Clear()`(protobuf 저장소 재사용), 직렬화 대상 `std::string* scratch` 재사용. ⚠️ protobuf·string·vector류는 **역대 최대 크기만큼 부풀어 유지**되므로, N회 사용마다 재생성하는 식의 주기적 리셋이 메모리에 도움이 될 수 있다.

### 4.5 불필요한 일 피하기

**성능 개선에서 가장 효과적인 범주 중 하나 — 안 해도 되는 일을 안 하는 것.** 흔한 경우 전용의 특화 경로, 사전 계산, 필요할 때까지 미루기, 덜 실행되는 코드로 끌어올리기가 모두 이 계열이다.

#### Fast path — 흔하고 단순한 경우를 빠르게

**코드는 모든 경우를 다루도록 작성되지만, 일부 경우는 훨씬 단순하고 훨씬 흔하다.** `vector::push_back`이 대표적 구도 — 대부분은 공간이 있고, 리사이즈 코드는 드물게만 필요하다. 사례들:

- **UTF-8 스캐너**: 4바이트 배수만 fast path로 처리하고 나머지를 느린 범용 루틴에 넘기던 것을, **끝에 남은 단일 ASCII 바이트까지 처리**하도록 확장 — 5바이트짜리 순수 ASCII 문자열이 더는 느린 경로로 빠지지 않는다.
- **InlinedVector::Resize**: 트랜잭션 객체들과 3개의 Span으로 일반화돼 있던 것을, 흔한 두 경우(축소/용량 내 확장)를 앞에 두는 단순 분기로 재작성.
- **TensorShape 초기화**: 모든 차원 크기가 16bit에 들어가는 흔한 경우에 1~4차원 각각의 전용 경로 추가.
- **⚠️ 역방향 사례 — fast path를 "줄여서" 빨라진 경우**: protobuf varint 파서의 인라인 fast path가 1바이트·2바이트 경우를 모두 다루던 것을 **1바이트만** 다루게 축소 — 인라인 코드가 작아져 코드 크기·icache 압박이 줄어 오히려 빨라졌다. fast path 설계는 "많이 덮을수록 좋다"가 아니라 균형점 문제라는 증거.
- **RPC 통계 합산**: 에러가 하나도 없었으면(`any_errors_set` 플래그) 에러 배열 합산 루프 전체를 건너뛴다.
- **조기 기각 필터**: soft token 판별에서 비싼 fingerprint 계산 전에 **첫 바이트 256칸 배열 조회**로 먼저 거른다 — soft token은 대부분 구두점 계열이라 첫 바이트만으로 대부분 기각된다.

#### Precompute — 한 번만 계산해 저장

- TensorFlow 실행기: 노드 속성(`kernel_is_expensive`, `is_async`, `is_merge`, `is_enter_exit_or_next_iter` 등)을 초기화 시점에 **비트필드로** 미리 계산 — 실행 hot path의 분기가 "특수 노드인가" 한 번으로 줄었다.
- 바이트 트라이그램 분류기: `Prob()` 변환을 **256칸 룩업 테이블**로 미리 계산해 이중 루프 안에서 배열 조회로.
- 일반 원칙: **입력 검증은 모듈 경계에서 한 번** — 내부에서 반복하지 마라.

#### Defer — 필요해질 때까지 미루기

원문에서 가장 극적인 수치가 여기 있다 — XLA `sharding_propagation.cc`: 조건 검사보다 **먼저** `GetSubSharding()`(비싼 호출)을 부르던 것을, 해당 operand일 때만 부르도록 순서 교체. 대형 컴파일 1건의 CPU **43.7초 → 2.0초**. 같은 계열: 할당/해제마다 통계를 갱신하지 않고, 훨씬 드물게 불리는 `Stats()` 호출 시점에 계산.

#### 루프 밖으로 — hoisting

루프 조건의 `src_shape.dimensions(...)` 호출을 루프 밖 지역 변수로. 버퍼 포인터도 루프 밖에서 미리 획득. (§4.6 컴파일러 협조와 연속선상 — 컴파일러가 스스로 못 하는 호이스팅을 사람이 해 주는 것.)

#### Specialize — 범용 코드의 일반성이 공짜가 아니다

- **히스토그램 출력**: 모니터링 시스템이 서버들을 긁을 때마다 불리는 `sprintf`(`StringPrintf`) 경로를, 실제 쓰이는 포맷 2종("%.0f"·"%.12g")만 다루는 전용 `FormatNumber`로 교체 — 정수면 `StrAppend`로 직행. **4배.**
- **VLOG(1), VLOG(2), …**: 레벨이 호출부 상수인 점을 이용해 `SlowIsEnabled0~5` 전용 함수로 분기 — 거의 모든 호출부에서 정수 인자 전달 코드가 사라진다(속도 + 코드 크기).
- **RE2 → prefix 매칭**: 정규식 접미부가 `.*`이면 `MATCH_TYPE_PREFIX` 전용 타입으로 분류해 `RE2::FullMatch`를 우회.
- **IP 포맷팅**: `StringPrintf` 대신 `StrCat`(IPv4는 옥텟 4개를 직접 조립).

#### Caching

큰 직렬화 proto의 반복 파싱을 **미리 계산된 fingerprint 키의 캐시**로 제거 (`fp_to_iometa` 맵 — 같은 매핑 proto가 반복 등장하는 워크로드).

### 4.6 컴파일러를 돕기

**컴파일러는 추상화 층을 뚫고 최적화하기 어렵다** — 코드 전체 행동에 대해 보수적 가정을 해야 하고, 속도/크기 트레이드오프를 다르게 잡을 수도 있다. 시스템의 행동을 더 잘 아는 프로그래머가 더 낮은 수준으로 고쳐 써서 도울 수 있다.

> ⚠️ **프로파일이 문제를 보여줄 때만 하라.** 컴파일러는 대개 알아서 잘한다. 성능 임계 루틴은 **생성된 어셈블리를 직접 보라** — pprof가 소스·디스어셈블리를 성능 데이터와 겹쳐 보여준다.

- **hot 함수 안의 함수 호출 제거** — 프레임 셋업 비용 회피. 극단 사례: 인라인 함수 안의 `ABSL_LOG(FATAL)`을 `ABSL_DCHECK(false)`로 바꿔 프레임 셋업 자체를 제거.
- **slow-path를 별도 tail-call 함수로 분리.**
- **작은 데이터를 지역 변수로 복사해 aliasing 가정 제거** — 자동 벡터화·레지스터 할당이 좋아진다. 사례: `ShapeUtil::ForEachState`가 들고 있던 `absl::Span` 3개를 **원시 포인터**로 교체(span의 operator[]보다 단순 배열 연산).
- **아주 뜨거운 루프는 손으로 언롤** — CRC32를 4바이트 → **16바이트 단위**(STEP 매크로 4연발)로. Spanner 키 파싱에서는 `memchr` 대신 4문자 단위 수동 언롤 + **뒤에서부터 스캔**(첫 구획이 가장 길고 '#'가 없다는 도메인 지식 활용).

### 4.7 통계·로깅 비용

**정보의 효용과 유지 비용을 저울질하라.** 통계·행동 정보는 고수준 동작을 이해하고 개선하는 데 유용하지만, 유지 비용이 hot path에 얹힌다. 성능 문서들이 잘 다루지 않는 축이다.

- **쓸모없는 통계는 아예 버린다.** SelectServer의 알람·클로저 개수 `MinuteTenMinuteHourStat` 제거 — 알람 설정 **771 ns → 271 ns** 개선의 일부. 저자 부연: 이 변수들을 가벼운 `Atomic32`로만 남겼어도 281 → 340 ns로 느려졌을 것 — "모니터링은 좋아 보이지만 실제로는 임계 네트워킹 코드에 상당한 오버헤드".
- **샘플링.** 요소 전수 대신 표본만 통계 유지(tcmalloc 할당 추적, /requestz, Dapper가 모두 이 방식). 사례 — 문서 정보 요청 처리마다 **히스토그램 39개**를 만지던 것을 표본 요청에만.
- **샘플링 레이트 인하 + 판정 비용 인하.** Google Meet 패킷 실행기 — COVID 초기 사용자 폭증을 감당하기 위한 작업. `ThreadCPUUsage()`(호출당 400ns+, `absl::Now`의 ~30배)의 샘플링을 1/10 → **1/32**로 낮추고, **2의 거듭제곱 모듈러**로 판정 자체도 싸게, 실행 시간 기록도 표본만: **224 ns → 85 ns (+62%)**.
- **지연 계산.** 할당·해제마다 갱신하지 말고 드물게 불리는 `Stats()`에서 계산 (§4.5 Defer와 동일 사례).
- **hot path에서 로깅 제거.** 로그가 안 찍히는 레벨이어도 `ABSL_VLOG`는 최소 load+비교이고, **로깅 코드의 존재 자체가 컴파일러 최적화를 방해**한다. 사례 셋 — GPU 할당기 내장 `VLOG(6)` 제거 / 이미지 유사도 이중 루프의 `VLOG_IS_ON(3)`을 **루프 밖에서 한 번** 판정(`const bool vlog_3`, +8~10%) / 판정 결과를 헬퍼 루틴들에 인자로 전달(`ScheduleAlarm(..., vlog_1)`).

### 4.8 코드 크기

**성능은 실행 속도만이 아니다.** 코드가 크면 컴파일·링크가 느려지고, 바이너리가 붓고, 메모리를 더 쓰며, **icache 압박과 분기 예측기 등 마이크로아키텍처 구조에 악영향**을 준다. 여러 곳에서 쓰일 저수준 라이브러리, 많은 타입으로 인스턴스화될 템플릿 코드에서 특히 중요하다. (기법은 언어별로 크게 다르며, 아래는 템플릿·인라인 남용에 시달리는 C++ 기준.)

**널리 인라인되는 코드를 다듬어라.** 널리 불리는 함수 × 인라인 = 코드 크기에 극적 영향.

- `TF_CHECK_OK`: 성공 경로에서 `Status::OK()` 객체 생성 자체를 없애고, 실패 시 포맷팅을 out-of-line 함수로 — 매크로가 `while (string* r = TfCheckOpHelper(val, #val)) LOG(FATAL) << *r` 형태로.
- `RETURN_IF_ERROR`: 전용 어댑터 클래스 + fast path에서 `StatusBuilder` 생성/소멸 제거 — **호출 지점마다 79바이트** 축소.
- `CHECK_GE` 계열: int-int 특수화를 out-of-line으로 — **4.5배 빨라지고 호출부 코드 125 → 77바이트**. 소멸자 제거의 논리가 흥미롭다: "str_이 non-NULL이면 어차피 LOG(FATAL) 직전이니 정리할 이유가 없다."
- protobuf 길이 인코딩: 128바이트 이상 메시지의 varint 길이 기록을 out-of-line 호출로 — 한 대형 바이너리에서 이 **한 줄**의 인라인 누적 코드가 5,454,640바이트였는데 9,609바이트로. "크고 중요한 바이너리들이 작아지고 **빨라지기까지** 했다."

**인라인은 신중하게.** 인라인은 종종 성능을 올리지만, 상응하는 이득 없이 코드만 키우거나 **icache 압박으로 오히려 성능을 해칠 수 있다.** TensorFlow에서 성능 비민감 함수(에러 경로·op 등록 코드)의 인라인을 중단하고 성능 민감 함수의 slow path를 non-inline 함수로 분리 — 심볼 크기 **12.2% 감소**(8,814,545 → 7,740,233바이트). `absl::flat_hash_map/set`도 타입 비의존 코드 추출 + `ABSL_ATTRIBUTE_NOINLINE` 배치로 대형 바이너리 ~0.5% 감소. 그 외: arena 미사용 시 string 할당/해제 비인라인화, `const char*` 오버로드 추가로 호출부마다의 `std::string` 생성 코드 제거.

**템플릿 인스턴스화를 줄여라.** 템플릿 코드는 인자 조합마다 복제된다. 사례 — `template <bool Split>`을 일반 인자 `bool split`로(한 번 문자열 상수 고르는 데만 쓰였으므로 런타임 분기면 충분): 대형 루틴 인스턴스 **287 → 143개**. 부피가 큰 코드는 템플릿 생성자에서 **비템플릿 공유 기반 클래스** 생성자로 이동, `<T, Device, Rank>` 조합별 → `<T>`별+`<Rank>`별로 축소.

**컨테이너 연산 호출 수 자체가 코드다.** 이모지 폴백 맵을 `(*map)[k] = v;` 수백 줄로 초기화하던 것을 **단일 bulk insert**로 — 많은 바이너리에 링크되는 라이브러리에서 텍스트 **188KB → 360바이트**. InlinedVector 연산을 잔뜩 쓰는 80줄 루틴을 .h에서 .cc로 이동(인라인 이득이 원래 없던 코드).

### 4.9 병렬화와 동기화

**병렬성 활용 — 항목이 아니라 배치 단위로 나눠라.** 현대 머신의 코어는 놀고 있는 경우가 많다. 항목별 병렬 실행 비용을 상쇄하려면 먼저 배치로 묶는다. 사례 — 토큰 인코딩 4-way 병렬화 **~3.6배**, 클러스터별 디코딩을 executor에 뿌리고 Notification으로 모으는 병렬화 **5배**. ⚠️ **여유 CPU가 없거나 메모리 대역폭이 포화면 병렬화는 도움이 안 되거나 해가 된다** — 시스템 성능으로 신중히 측정하라.

**락 획득 상각.** hot path의 Mutex 연산 비용을 줄이기 위해 잘게 쪼개진 락킹을 피하라 — 쿼리 노드 트리 해제 시 **노드마다 락을 다시 잡던 것을 트리 전체에 한 번**으로(`Release` → `ReleaseLocked` 재귀). ⚠️ 락 경합을 늘리지 않는 경우에만.

**임계 구역은 짧게.** 임계 구역 안에서 비싼 일을 피하라 — 특히 **무해해 보이지만 RPC를 하거나 파일을 만지는 코드**를 조심. 사례 둘 — ① mutex를 쥔 채 파라미터 서버에 진행 상황 RPC를 보내던 것을, 락 안에서는 판단만 하고 RPC는 락 밖에서 ② ML 학습 실행기의 임계 구역이 만지는 캐시라인 수를 노드 속성 비트 사전 계산 + 목적지 NodeItem 직접 참조로 축소(엣지 데이터 접근이 ~2 + O(출력 엣지 수) 캐시라인 → 1~2개, TLB 압박도 감소) — 학습 실행 **+3.3%**. ⚠️ `~MutexUnlock` 직전에 도는 **비싼 소멸자**도 임계 구역 안이다 — 그런 객체는 `MutexLock`보다 먼저 선언해 두는 게 도움이 될 수 있다.

**샤딩으로 경합 감소.** 경합 심한 Mutex 보호 자료구조를 샤드별 Mutex의 N개 샤드로 분할 — **전제: 샤드 간 불변식이 없어야 한다.** 사례 — LRU 캐시 16-way 샤딩으로 멀티스레드 throughput **~2배**, Spanner ActiveCallMap 64샤드 분할로 8192 fiber 벤치마크 wall-clock **-69%**. 맵이라면 concurrent hash map도 고려. ⚠️ **샤드 선택에 쓴 정보를 조심하라** — 해시 값의 특정 비트를 샤드 선택에 쓰고 그 비트가 하위 해시테이블에서 재사용되면, 왜곡된 해시 분포를 보게 된다(원문 사례는 `hasher({index, 42})`로 별도 해시를 만들어 해결).

**SIMD.** 여러 항목을 SIMD 명령으로 한 번에 처리할 수 있는지 탐색하라 (§4.12 SwissTable 참조).

**False sharing 감소.** 다른 스레드가 다른 가변 데이터를 만진다면 서로 다른 캐시라인에 배치 — C++에선 `alignas(ABSL_CACHELINE_SIZE)`. 사례 — Histogram에서 자주 변이되는 필드들(buckets_, min/max/count/sum)을 전용 캐시라인으로 분리. ⚠️ 이 지시자는 오용하기 쉽고 객체 크기를 크게 불릴 수 있다 — **측정이 정당화할 때만.**

**컨텍스트 스위치 빈도 감소.** 작은 작업은 디바이스 스레드풀에 넘기지 말고 **인라인 처리** — cast 연산에서 입출력 합계 16KB 미만이면 현재 스레드에서 바로 수행.

**파이프라이닝에는 버퍼드 채널.** 언버퍼드 채널은 reader가 준비될 때까지 writer를 블록한다 — 동기화 용도면 유용하지만, **병렬성을 늘리려는 용도면 버퍼를 줘라.**

**Lock-free는 상위 추상화로.** 읽기 수천 회/초·쓰기 드묾인 RPC 스텁 캐시를 lock-free 맵으로 바꿔 탐색 latency **3~5%** 감소, 토큰 유효성 판별에 고정 렉시콘 + lock-free 해시맵(epoch GC 기반) 사례도. ⚠️ **원자 변수 직접 조작은 위험하다 — 더 높은 수준의 추상화를 선호하라.**

### 4.10 Protocol Buffer

**protobuf는 전송·영속화에는 편리하지만 상당한 성능 비용이 있다.** 문서에서 가장 큰 단일 수치가 여기 있다 — 점 1,000개를 채우고 Y좌표를 합산하는 코드를 protobuf에서 **C++ struct의 `std::vector`**로 바꾸니 **20배**:

```
name                old time/op   new time/op   delta
BenchmarkIteration  17.4µs ± 5%   0.8µs ± 1%    -95.30%  (p=0.000 n=11+12)
```

게다가 protobuf 버전은 바이너리에 수 KB의 코드·데이터를 더한다 — 타입이 많은 시스템에서 빠르게 누적되어 icache/dcache 압박을 만든다. 원문의 조언 목록:

- **불필요하게 쓰지 마라.** 직렬화/파싱을 안 할 데이터라면 protobuf에 넣지 마라. DebugString이나 복사 가능성 같은 "부가 편의"만 원하면서 20배 비용을 무는 것.
- **불필요한 메시지 계층을 피하라.** `Foo{Bar{Baz{count}}}` 대신 `Foo{count}` — 중간 메시지마다 할당/해제, 함수 호출, cache miss, 더 큰 직렬화 결과가 붙고 모든 연산(파싱·직렬화·size)이 메시지 트리를 순회해야 한다.
- **자주 나오는 필드에 작은 필드 번호를.** 필드 번호+와이어 포맷은 varint로 인코딩된다 — **1~15는 1바이트, 16~2047은 2바이트** (2048+는 피하라). 성능 민감 proto에는 미래 확장용으로 작은 번호 몇 개를 예약해 두는 것도 고려.
- **int32/sint32/fixed32를 가려 써라.** 기본은 int32/int64. 해시 코드처럼 큰 값은 **fixed32/fixed64**(varint는 큰 값에서 더 크고 디코딩도 비싸다), 자주 음수인 값은 **sint32/sint64**.
- **proto2 반복 숫자 필드는 `[packed=true]`.** 기본 직렬화는 (tag, value) 쌍의 나열이라 원소마다 태그를 디코드한다. packed는 길이 + 값들 — proto3는 기본. 고정폭 타입(fixed32/float/double)과 특히 궁합이 좋다(원소 수 × 크기로 전체 길이가 즉시 계산).
- **바이너리 데이터·큰 값은 string 대신 bytes.** string은 UTF-8 텍스트용이라 검증이 붙을 수 있다.
- **`string_type = VIEW`로 복사 회피.** 큰 bytes/string 필드는 파싱 시 원본에서 복사되는데, VIEW 주석 + `ParseFromStringWithAliasing`류는 `absl::string_view`로 원본 backing string을 참조만 한다 — 단, backing string이 proto 객체보다 오래 살아야 한다.
- **큰 필드에 `[ctype=CORD]` 고려.** 필드 표현이 `std::string` → `absl::Cord`(참조 카운트 + 트리 저장)로 바뀌어 복사·append 비용이 준다. Cord로 직렬화된 버퍼에서 파싱하면 복사 회피. 성능은 길이 분포·접근 패턴에 달렸으니 **벤치마크로 검증하라.**
- **C++에선 arena를 써라.** message·string 필드는 (최상위가 스택이어도) 힙 할당이다 — arena가 할당을 상각하고 해제를 사실상 공짜로 만들며 지역성도 개선. repeated/string/message 필드가 많을수록 효과.
- **.proto 파일을 작게.** 한 파일에서 뭐 하나만 참조해도 **링커가 파일 전체를 끌어온다** — 빌드 시간과 바이너리 크기. 큰 파일에의 하드 의존을 피하려면 extension·Any 활용.
- **메모리에서도 직렬화 형태 보관을 고려.** 인메모리 protobuf 객체는 풋프린트가 크고(**흔히 와이어 포맷의 5배**) 여러 캐시라인에 흩어진다 — 오래 살릴 객체가 많다면 직렬화 형태로.
- **map 필드를 피하라.** 성능 문제가 문법적 편의를 압도한다 — `repeated Var { key; value; }`로 받고 비-protobuf 맵을 초기화하라.
- **부분 파싱: 서브셋 메시지.** 100개 필드 중 2개만 필요하면, 그 필드 번호만 가진 자체 메시지 타입(`SubsetMessage`)으로 파싱 — 나머지는 unknown field 처리된다. unknown field를 버리는 API를 쓰면 더 빠르다.
- **재사용.** proto 객체는 루프 밖에 선언해 저장소를 반복 재사용 (§4.4와 동일).

### 4.11 C++ 타입 선택

**표준 컨테이너의 기본값이 최선이 아닐 때가 많다.** 각 타입의 "왜"와 함께:

| 타입 | 왜 / 사례 |
|---|---|
| `absl::flat_hash_map/set` | `std::map`·`std::unordered_map`보다 대체로 빠름(플랫 저장 + SwissTable). `__gnu_cxx::hash_map` → 교체만으로 `BM_CodeToLanguage` **19.4 → 10.2 ns (-47.5%)** |
| `absl::btree_map/set` | 정렬 순회가 필요할 때 — 트리 노드당 **여러 엔트리**를 저장해 `std::map` 대비 자식 포인터 오버헤드가 줄고, 엔트리가 메모리에 연속이라 캐시 효율이 좋다. 헤비한 work-queue의 `std::set` → `btree_set` 사례 |
| `util::bitmap::InlinedBitVector` | 짧은 비트벡터를 인라인 저장 — `std::vector<bool>`보다 나은 선택인 경우가 많고, `FindNextSetBit`로 "다음 관심 항목" 순회도 빠르다 |
| `absl::InlinedVector` | 원소가 적을 때 backing 배열 할당을 아예 회피 (개수는 둘째 템플릿 인자) |
| `gtl::vector32` | 크기를 32bit로 제한한 벡터 — **타입 교체 하나로 Spanner에서 ~8TiB 절감** (`std::vector<FamilyId>` → `gtl::vector32<FamilyId>`, getter는 `absl::Span` 반환으로) |
| `gtl::small_map` | 소수 원소는 인라인 배열, 넘치면 지정한 맵 타입으로 자동 승급 |
| `gtl::small_ordered_set` | 보통 작은 정렬 집합용 — set은 큰 데이터셋에 최적화돼 있어, 작은 집합엔 고정 배열이 캐시 풋프린트와 임계 구역 길이를 줄인다 (listener 집합 사례) |
| `gtl::intrusive_list` | 링크 포인터를 원소 안에 내장한 이중 연결 리스트 — `std::list<T*>` 대비 **원소당 캐시라인 1개 + 간접 참조 1회** 절약 |

**`absl::Status`/`StatusOr`는 hot 루틴에서 제한하라.** 꽤 효율적인 타입이지만 **성공 경로에서도 비용이 0이 아니다.** 의미 있는 에러 정보가 필요 없거나 실패할 수 없는 루틴에서는 피할 것.

- `RoundUpToAlignment`: `StatusOr<int64>` 반환 + RET_CHECK → 사전조건을 DCHECK로 문서화한 인라인 int64 함수로.
- `ShapeUtil::ForEachIndexNoStatus`: 텐서 **원소마다** `StatusOr<bool>` 생성·소멸이 붙던 순회에 plain bool 변형 추가.
- RPC hot path의 `StatusOr` 제거로 **14% CPU 회귀 해소** — 대안은 enum 결과 코드 + 출력 인자.

### 4.12 Bulk operations

**항목을 하나씩이 아니라 여러 개를 한 번에 다뤄라.**

- `absl::flat_hash_map`(SwissTable): 키 그룹의 해시 바이트들을 **SIMD 명령 하나로 동시 비교**(`_mm_cmpeq_epi8` + movemask). Kulukundis의 CppCon 2017/2019 강연 참조.
- ordered-code 인코딩: 바이트마다 "무엇을 할지 검사"하던 루프를 **BigEndian::Store로 한 번에 쓰고 길이만 계산해 보정**하는 방식으로.
- Reed-Solomon: 인터리브된 입력 버퍼 여러 개를 청크로 묶어 처리 — **+10.5~40.2%**.
- **GroupVarInt** (circa 2004): 가변 길이 정수를 하나씩이 아니라 **4개 그룹**(5~17바이트)으로 인코딩/디코딩하는 포맷 도입 — 그룹 디코딩이 개별 varint 4개의 **~1/3 시간**. 유사하게 k-bit 숫자 4개 단위의 KBitStream 인코더/디코더(K가 컴파일 타임 상수라 짝수 k는 항상 바이트 정렬, 홀수 k는 니블 정렬을 가정할 수 있다).

### 5.2 이 표에서 읽히는 것

> **① 가장 큰 이득은 "표현을 바꾸는 것"에서 나온다.** 50배(알고리즘 교체), 20배(protobuf→struct), 21.9배(지연), 4배(특화) 모두 **더 잘 짜서**가 아니라 **다른 것을 쓰기로 해서** 얻었다. 미시 최적화는 대체로 10~30% 대에 머문다.
>
> **② 통계·로깅이 의외로 큰 항목이다.** 771→271 ns, 224→85 ns는 **기능이 아니라 계측 때문에** 나가던 비용이다. 성능 논의에서 자주 빠지는 축이다.
>
> **③ 그럼에도 저자들은 3~5%짜리를 함께 싣는다.** §2 통찰 2("1% 개선 20개")와 일관된 편집 방침이다. **작은 수치를 부끄러워하지 않는 것 자체가 이 문서의 주장**이다.

### 5.3 복합 CL 사례 — "병목을 찾은 뒤의 마인드셋"

원문은 여러 기법이 한 CL에 함께 등장하는 사례들을 별도 절로 모아 두었다 — "병목이 식별된 뒤 시스템 일부를 전반적으로 빠르게 만드는 마인드셋"을 배우는 자료로.

**GPU 메모리 할당기 ~40~48% (e2e 학습 +2.9%).** ① Chunk를 포인터가 아닌 **핸들(vector 인덱스)**로 식별 — next/prev가 8바이트 → 4바이트, 저장이 연속 ② Chunk 객체 **free list 재사용**으로 힙 할당 제거 ③ bin 탐색을 `std::set::lower_bound`에서 **log₂(size/256) 인덱스 배열**로 — 비트 연산 몇 개로 bin 도달, Bin 저장도 연속 배열(멀티스레드 시 코어 간 캐시라인 이동 감소) ④ retry_helper를 우회하는 **fast path** 추가(std::function 할당 회피) ⑤ VLOG 주석 처리. + 경합 벤치마크 신설.

**Pathways 전송 처리량 +20%.** 특수 파싱 함수들을 `ParsedDescriptor` 클래스로 통합(전체 파싱 회피) · proto 필드 string → bytes(**불필요한 UTF-8 검사 제거**) · 작은 텐서용 필드를 Cord → string · `unordered_map` → `flat_hash_map` · Stack op에 `LookupMany` 적용(배치 원소당 → 배치당 락) · 불필요한 string 생성 제거.

**XLA 대형 컴파일 +31% (전체 프로그램 +19%: 573s → 465s).** `ForEachState`의 Span → 원시 포인터 · 루프 밖 span/포인터 사전 구성 · `ForEachIndexNoStatus` 도입(원소당 StatusOr 소멸자 제거) · `Broadcast`를 원소 바이트 크기(1/2/4/8)별 템플릿 특화 — 런타임 변수 memcpy가 상수 크기 복사로 · **호출당 ~(5 + 차원수 + 원소수)번의 가상 호출**을 `shape()` 1회로 · 1차원 소스 특수화. Broadcast 마이크로벤치 +58%.

**MapReduce wordcount 2배 (12.56s → 6.55s).** 콤바이너를 `hash_multimap<Key, StringPiece>`(값마다 해시 엔트리) → `hash_map<Key, ValuePtr*>`(값은 **반복 카운트를 가진 연결 리스트**)로 — 메모리 대폭 감소(플러시 빈도 감소), 기존 키에 값 추가 시 해시 엔트리 생성 회피, `Output(key,"1")` 5연발이 반복 카운트 5의 엔트리 하나로. + reduce 샤드가 1개면 키 fingerprint 생략, hot path의 VLOG(3) → DVLOG(3).

**2001년 인메모리 인덱스 서빙 3.3배 (150 → 500+ qps, 듀얼 Pentium III·2GB 인덱스).** 디스크 → 인메모리 전환 계획에서 드러난 문제들의 일괄 수정 — 디코딩 중 체크섬 검증으로 **이후 모든 getsymbol의 경계 검사 제거** · BitDecoder 필드를 루프 전체에서 지역 변수에 유지하는 매크로 · `bsf` 인라인 어셈블리 · 벡터를 루프 밖에서 resize하고 포인터로 채움 · docid를 **로컬 공간에 유지**(필요할 때만 num_shards_ 곱하기) · `AdvanceToDocid` 인터페이스로 로컬 docid 스캔 허용 · 위치 데이터 **on-demand 디코딩** · 페이지 경계 4바이트 이내 블록은 로컬 버퍼 복사(mmap 페이지 밖 4바이트 load의 segfault 걱정 제거) · 스코어링 구조를 MAX_TERMS가 아닌 **nterms_개만 초기화**(문서당 20~100KB memset 제거) · 값이 0이면 round_to_int와 후속 계산 생략 · 경계 검사를 디버그 어서션으로.

**Google Meet ScopedLogId +52%.** 불변식 위반 감시용이던 `LOG_EVERY_N(ERROR)` 제거 → 작아진 Push/PopLogId 인라인화 → `InlinedVector`를 **고정 배열 4칸 + int size**로(4를 넘은 적이 없었으므로 — 필요 이상의 일반성 제거).

## 6. Key Takeaways

1. **"나중에 프로파일링하자"의 진짜 대가는 느린 코드가 아니라 평평한 프로파일이다.** 성능이 여기저기서 조금씩 새면 뚜렷한 hotspot이 없어 **어디서 시작할지조차 알 수 없다**. 그 상태의 나머지 셋 — 고칠 사람과 겪는 사람의 분리, 사용 중 시스템의 경직, overprovisioning으로 덮기 — 이 저자들이 사전 고려를 주장하는 이유다.

2. **처방은 "최적화하라"가 아니라 "기본값을 잘 고르라"다.** *"가독성·복잡도를 크게 해치지 않는다면 더 빠른 쪽을 고르라."* 코드의 종류(테스트/앱/라이브러리)에 따라 고민의 깊이를 조절하되, 라이브러리 코드에서는 `InlinedVector` 같은 선택이 **비지역적 복잡도 없이** 출발선을 높인다.

3. **측정 전에 추정이 온다.** 코드가 없는 설계 시점에는 프로파일러가 무력하다. quicksort 예제에서 **지배 항이 메모리(7.5s)가 아니라 분기 예측 실패(75s)** 임을 코드 없이 알아낸 것이 추정의 값어치다. 이를 위해 저수준 비용표에 더해 **자기 시스템의 상위 연산 비용표**를 갖고 있어야 한다.

4. **가장 큰 이득은 표현을 바꾸는 데서 나온다.** 50배(알고리즘 교체), 20배(protobuf→struct), 21.9배(계산 지연), 4배(특화)는 모두 "더 잘 짜기"가 아니라 **"다른 것을 쓰기"** 였다. 프로파일이 평평하면 미시 최적화가 아니라 **콜스택 위쪽의 구조**를 봐야 하는 이유다. 데드락 탐지 사례의 보너스 — 좋은 알고리즘은 인위적 한계(2K 제한)를 없애 **정확성 버그(잠복 데드락)까지 드러냈다.**

5. **계측 비용은 기능 비용만큼 크다.** 알람 771→271 ns, 패킷 224→85 ns는 전부 **통계 수집을 줄여서** 얻었다. 쓸모없는 통계는 버리고, 필요하면 샘플링(판정도 2^n 모듈러로 싸게)하고, 갱신은 `Stats()` 호출 시점으로 미뤄라. 로깅은 안 찍혀도 비용이고(load+비교), **존재만으로 컴파일러 최적화를 막는다.**

6. **성능은 실행 속도만이 아니다 — 코드 크기도 성능이다.** protobuf 길이 인코딩 **한 줄**이 한 바이너리에서 5.4MB의 인라인 코드였다. 인라인·템플릿 인스턴스화·컨테이너 연산 호출 수는 컴파일 시간, 바이너리 크기, **icache 압박과 분기 예측기**에 직결된다. varint 파서는 fast path를 **줄여서**(2케이스→1케이스) 빨라졌다.

7. **작은 개선을 부끄러워하지 말라 — 문서의 편집 방침 자체가 주장이다.** Knuth의 "쉽게 얻은 12%는 결코 사소하지 않다"처럼, 저자들은 3.3%짜리 CL을 50배짜리와 나란히 싣는다. **1%짜리 20개면 상당한 폭**이고, 그 작업에는 **안정적이고 품질 좋은 마이크로벤치마크**가 전제다. §5.3의 복합 CL들이 그 실물 — 큰 승리 하나가 아니라 5~10개의 작은 결정이 겹쳐 40~330%가 된다.

8. **범위를 명확히 알고 읽어야 한다.** 이 문서는 **단일 바이너리의 일반 튜닝**만 다룬다. 분산 시스템과 ML 하드웨어 성능은 "그 자체로 거대한 영역"이라며 명시적으로 제외한다. 더 읽을 것으로 저자들이 꼽는 목록: Agner Fog *Optimizing software in C++*, Richard Sites *Understanding Software Dynamics*, Bentley *Programming Pearls*, Warren *Hacker's Delight*, Hennessy & Patterson, Lemire 블로그 등.

## 7. 이 저장소의 다른 문서와의 연결

> 이 절은 원문에 없다. 이 저장소의 기존 문서와 대응시켜 정리했다.

MixLM 요약의 **§7 서빙 스택**(LinkedIn SGLang 블로그 2편)은 사실상 이 카탈로그의 **실전 적용 사례집**이다. 대응이 거의 일대일이다.

| Performance Hints 기법 | [`../2026-08-02/mixlm.md`](../2026-08-02/mixlm.md) 의 대응 |
|---|---|
| **Bulk API** (§4.1) | §7.5 Stage 1 — 순차 tokenization → **batch tokenization** (PR #5141), Async Dynamic Batch Tokenizer (P99 4,583→464 ms) |
| **API 경계 넘기 비용** (§4.1) | §7.5 — 배치를 ZMQ로 개별 전송해 배치 구조가 소실되던 문제를 **단일 메시지 전송**으로 (70.39→41.12 ms) |
| **Specialize code** (§4.5) | §7.5 Stage 2 — 범용 생성 경로 대신 **scoring 전용 실행 경로**. decode·sampling·KV 갱신 제거하되 **정확한 동치성 유지** (P99 6,220→454 ms) |
| **통계 수집 비용** (§4.7) | §7.5 Stage 2 — **per-token logprob 추출 생략**, 작은 memcpy 다수를 단일 vectorized gather로 |
| **Precompute / 캐싱** (§4.5) | §4.2 MixLM 본체 — item을 **오프라인 인코딩해 nearline cache**에 저장. 논문 전체가 이 기법의 대규모 적용이다 |
| **Defer expensive computation** (§4.5) | §7.6 Knock-Knock — retrieval 중에 user context prefill을 **미리** 돌려 시간 뒤로 숨김 (520→200 ms) |
| **경합 감소 / 병렬화** (§4.9) | §7.5 Stage 4 — Python **GIL 우회**를 위한 multi-process gRPC, GPU당 스케줄러 다중화 (+40%) |
| **평평한 프로파일 대응** (§2) | §7.5 전체 — *"each optimization exposed the next ceiling."* 4단계에 걸쳐 병목이 GPU → CPU → Python 런타임으로 이동한 과정이 이 절의 교과서적 사례다 |
| **자기 워크로드의 비용을 알라** (§2) | Blog B 결론 — *"optimization is only as good as how well you profile and understand the workload characteristics"* |

> **한 가지 어긋나는 지점.** Performance Hints는 **정밀도 저하를 논하지 않는다**(무손실 최적화 전제). 반면 MixLM §7.7의 FP8 사례는 **랭킹 점수가 단일 토큰의 상대 확률이라 양자화 오차에 민감**하다는, ML 서빙 고유의 축을 보여준다. 이 문서가 명시적으로 제외한 "ML 하드웨어 성능" 영역과 맞닿는 부분이다.
