## 1. Background

### "성능은 나중에" 가 틀리는 이유

Knuth의 문장은 늘 잘려서 인용된다. 전문은 이렇다.

> "We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. **Yet we should not pass up our opportunities in that critical 3%.**"

저자들은 오히려 다른 Knuth 인용을 앞세운다 — **12% 개선을 하찮게 보는 통념에 대한 반박**이다.

> "In established engineering disciplines a **12% improvement, easily obtained, is never considered marginal**; and I believe the same viewpoint should prevail in software engineering."

"일단 단순하게 짜고 나중에 프로파일링해서 고치자"는 접근이 실패하는 지점은 네 가지다.

| # | 실패 양상 | 왜 문제인가 |
|---|---|---|
| 1 | **프로파일이 평평해진다(flat profile)** | 성능이 여기저기서 조금씩 새면 뚜렷한 hotspot이 없다. **어디서 시작할지조차 알 수 없다** |
| 2 | **고칠 사람과 겪는 사람이 다르다** | 라이브러리라면 성능 문제를 겪는 쪽은 남의 코드를 읽고 그 팀과 협상해야 하는 사람이다 |
| 3 | **이미 쓰이는 시스템은 바꾸기 어렵다** | 사용량이 많아진 뒤에는 큰 변경 자체가 불가능해진다 |
| 4 | **비싼 우회로로 덮게 된다** | 쉽게 고칠 수 있었을 문제를 과도한 replication이나 overprovisioning으로 때운다 |

> **저자들의 처방은 온건하다** — "가독성·복잡도를 크게 해치지 않는다면, 코드를 쓸 때 더 빠른 쪽을 고르라." 전면적 최적화가 아니라 **기본값 선택의 문제**로 프레이밍한다.

## 2. Motivation

### 핵심 통찰 1: 측정하기 전에 추정할 수 있어야 한다

프로파일링은 코드가 있어야 가능하다. 그런데 **설계 시점에는 코드가 없다.** 그래서 저자들은 **back-of-the-envelope 계산**을 앞세운다.

```
① 저수준 연산이 몇 번 일어나는지 센다 (disk seek 수, network round-trip 수, 전송 바이트 수 …)
② 각 연산의 대략적 비용을 곱한다
③ 더한다  →  자원 사용량(resource usage)

* latency 가 궁금하고 시스템에 동시성이 있다면, 겹치는 비용을 고려해 조금 더 계산해야 한다
```

**연산별 대략 비용** (2007년 Stanford 강연 표의 갱신판):

```
L1 cache reference                             0.5 ns
L2 cache reference                             3 ns
Branch mispredict                              5 ns
Mutex lock/unlock (uncontended)               15 ns
Main memory reference                         50 ns
Compress 1K bytes with Snappy              1,000 ns
Read 4KB from SSD                         20,000 ns
Round trip within same datacenter         50,000 ns
Read 1MB sequentially from memory         64,000 ns
Read 1MB over 100 Gbps network           100,000 ns
Read 1MB from SSD                      1,000,000 ns
Disk seek                              5,000,000 ns
Read 1MB sequentially from disk       10,000,000 ns
Send packet CA->Netherlands->CA      150,000,000 ns
```

> **저수준 표만으로는 부족하다.** 저자들은 **자기 시스템의 상위 연산 비용**도 함께 추적하라고 말한다 — SQL point read 한 번, Cloud 서비스 왕복 한 번, HTML 한 장 렌더링. *"If you don't know the relevant cost of different operations, you can't do decent back-of-the-envelope calculations!"*

#### 예제 A: 40억 바이트(10억 개 × 4B) quicksort

```
가정: quicksort 는 크기 N 배열을 log(N) 번 훑는다, 코어당 메모리 대역폭 ~16GB/s

메모리 전송 : 4GB / 16GB/s = 0.25s per pass × ~30 passes = ~7.5s
분기 예측실패: N·log(N) = ~30e9 회 비교, 그 절반이 실패라 가정
              15e9 × 5ns                              = 75s
                                                  합계 ≈ 82.5s
```

> **지배 항이 메모리가 아니라 분기 예측 실패다.** 32MB L3 캐시를 고려하면 마지막 22 pass는 캐시에서 돌아 메모리 전송이 7.5s → **2.5s**로 줄지만, 75s 앞에서는 의미가 없다. **추정의 값어치는 정밀도가 아니라 "무엇이 지배하는지"를 먼저 알려주는 데 있다.**

#### 예제 B: 썸네일 30장짜리 웹페이지

| 설계 | 계산 | 결과 |
|---|---|---|
| 디스크에서 **순차** 읽기 | (seek 5ms + 전송 10ms) × 30장 | **450 ms** |
| **K개 디스크에 분산**해 병렬 읽기 | 자원 사용량은 같고 latency만 ~1/K | 디스크 수백 개면 **~15 ms** |
| 전부 **단일 SSD**에 | (20µs + 1ms) × 30장 | **~30 ms** |

> 자원 사용량과 latency를 분리해 계산하는 시범이다. 병렬화는 **자원을 줄이지 않고 latency만** 줄인다.

### 핵심 통찰 2: 프로파일이 평평할 때가 진짜 문제다

저수확 과일을 다 딴 뒤에는 CPU 프로파일에 뚜렷한 봉우리가 없다. 저자들이 제시하는 대응은 여섯 가지다.

| 대응 | 내용 |
|---|---|
| **작은 개선을 무시하지 말 것** | 1% 개선 20개면 상당한 폭이 된다. 다만 **안정적이고 품질 좋은 마이크로벤치마크**가 전제다 |
| **콜스택 위쪽의 루프를 찾을 것** | flame graph가 유용. 루프 구조 자체를 재편할 여지를 본다 |
| **한 걸음 물러나 구조를 볼 것** | 미시 최적화 대신 콜스택 상단의 구조 변경. 알고리즘 개선이 여기 해당 |
| **지나치게 일반적인 코드를 찾을 것** | 단순 prefix 매칭이면 되는 곳에 정규식을 쓰고 있지 않은지 |
| **할당 프로파일을 볼 것** | ① 할당기 시간 자체가 줄고 ② **tcmalloc에서는 할당마다 다른 캐시라인으로 가므로 cache miss도 함께 준다** |
| **하드웨어 카운터 프로파일** | cache miss율이 높은 함수를 짚어준다 |

> **프로파일링은 성능 작업만을 위한 게 아니다.** 저자들은 **낯선 코드베이스를 파악하는 수단**으로도 프로파일링을 권한다 — 동적 콜그래프에서 비중 높은 루틴을 읽으면 "이 프로그램이 실제로 무엇을 하는가"의 감이 잡히고, 그 감이 낯선 코드를 고칠 자신감이 된다.

## 3. Contributions

1. **추정 우선의 성능 문화**: 측정 이전에 back-of-the-envelope으로 대안을 걸러내는 절차와, 그에 필요한 연산 비용표 제공.
2. **기법 카탈로그**: API 설계 · 알고리즘 · 메모리 표현 · 할당 · 불필요한 일 제거 · 컴파일러 협조 · 코드 크기 · 병렬화 · protobuf · C++ 타입 선택의 10개 축.
3. **모든 기법에 실제 CL과 벤치마크를 붙임**: 주장마다 Google 내부의 실제 변경과 수치가 근거로 달려 있다. 원칙 나열에 그치지 않는다.
4. **평평한 프로파일 대응법**: 대부분의 성능 문서가 다루지 않는, "쉬운 것을 다 한 뒤"의 전략.

## 4. Method — 기법 카탈로그

### 4.1 API 설계

**전제**: 성능 개선은 **캡슐화 경계 안에서** 끝나도록 코드를 조직하라. 모듈이 **deep**할수록(좁은 인터페이스 뒤에 많은 기능) 쉬워진다.

> ⚠️ **기능 추가 압력을 경계하라.** 널리 쓰이는 API에 기능을 더하면 미래 구현을 제약하고 **그 기능이 필요 없는 사용자에게까지 비용을 물린다.** 예 — C++ 표준 라이브러리 컨테이너 상당수가 **iterator 안정성**을 약속하는데, 이 때문에 일반적 구현에서 할당 횟수가 크게 늘어난다. 정작 대다수 사용자는 포인터 안정성이 필요 없다.

| 기법 | 내용 |
|---|---|
| **Bulk API** | API 경계를 넘는 비용을 줄이고 알고리즘적 이득도 얻는다. 예: `MemoryManager::LookupMany`. **부수 효과** — bulk 버전을 만들면서 시그니처도 단순해졌다. 클라이언트가 알아야 할 것은 "전부 찾았는가"뿐이어서 `Status` 대신 `bool`을 반환 |
| **View 타입** | `std::string_view`, `Span<T>` — 인자 전달에서 불필요한 복사 제거 |
| **미리 할당·계산된 인자** | 호출자가 버퍼를 넘기게 해 내부 할당을 없앤다 |
| **Thread-compatible > Thread-safe** | 대부분의 타입은 **외부 동기화 전제(thread-compatible)** 로 두는 편이 낫다. thread-safe로 만들면 **단일 스레드 사용자까지 동기화 비용을 문다** |

### 4.2 알고리즘 개선

> **가장 큰 기회지만, 안정된 코드에서는 드물다.** 새 코드를 쓸 때 주의를 기울일 값어치가 있다.

| 사례 | 변경 |
|---|---|
| 사이클 탐지 | 노드·엣지를 하나씩 추가 → **reverse post-order로 그래프 전체를 한 번에** 투입해 사이클 탐지를 자명하게 만듦 |
| 정렬 리스트 교집합 | O(N log N) → **해시 테이블 조회 O(N)** |
| IntervalMap | O(log N) 조회 → **해시 테이블 O(1)** |
| 검색 순서 (2000년경) | 작은 title/anchor 티어를 먼저 → **큰 full-text 티어를 먼저.** full-text 끝에 도달하면 그 부분집합인 title/anchor 티어를 **통째로 건너뛸 수 있다** → **throughput +19%** |

### 4.3 메모리 표현

목표는 **만지는 캐시라인 수를 줄이는 것**이다. 그러면 ① cache miss를 피하고 ② **메모리 버스 트래픽이 줄어 같은 기계의 다른 프로그램까지 빨라진다.**

| 기법 | 내용 |
|---|---|
| **Compact data structures** | 자주 접근하거나 메모리를 많이 차지하는 데이터는 조밀하게. **단, 캐시라인 경합 주의** |
| **Memory layout** | 정렬 기준으로 필드 재배치, **hot/cold 데이터 분리** |
| **포인터 대신 인덱스** | 64bit 포인터 → 32bit 인덱스. 참조가 작아지고 `T[]` 저장이 **연속적**이라 지역성도 좋아진다 |
| **Batched storage** | 원소마다 객체를 할당하는 `std::map`·`std::unordered_map` 회피 → `std::vector`·`absl::flat_hash_map`. 청크 단위 분할은 **점근 성능을 유지한 채** 캐시 발자국을 크게 줄인다 |
| **Inlined storage** | 보통 원소 수가 적은 컨테이너는 `absl::InlinedVector` |
| **중첩 맵 평탄화** | `btree<a, btree<b,c>>` → `btree<pair<a,b>, c>` |
| **Arena** | 할당 비용 절감 + **독립적으로 할당된 것들을 물리적으로 인접 배치** |
| **맵 대신 배열** | 키 도메인이 작은 정수면 배열 |
| **집합 대신 비트벡터** | `InlinedBitVector`. 합집합=OR, 교집합=AND로 집합 연산도 효율적 |

> ⚠️ **중첩 맵 평탄화는 양날이다.** 첫 키가 크면 반대로 가야 한다. 원문 사례 — (문자열 경로 + 숫자 서브키) 단일 해시테이블을, **경로로 1단계 / 서브키로 2단계**로 쪼갰더니 **마이크로벤치마크 +76%**. 경로 하나당 평균 1000개 키가 붙어 있어 **경로 저장 메모리가 1/1000로** 줄었고, 같은 경로의 서브키를 몰아서 접근할 때도 빨라졌다.

**비트벡터 실측** — Spanner 배치 시스템에서 `dense_hash_set<ZoneId>` → `InlinedBitVector<256>`:

```
BM_Evaluate/1      960 →  676   +29.6%
BM_Evaluate/2     1661 → 1138   +31.5%
BM_Evaluate/5     3780 → 2665   +29.5%
BM_Evaluate/20   17922 → 12338  +31.2%
BM_Evaluate/40   36836 → 26430  +28.2%
```

### 4.4 할당 줄이기

| 기법 | 사례와 수치 |
|---|---|
| **불필요한 할당 제거** | 정적 데이터 재사용. 웹서버 파스트리 풀 초기 크기 **200 → 10** 으로 낮춰 **CPU −7.5%** |
| **resize / reserve** | 컨테이너 크기를 미리 잡는다 |
| **복사 대신 이동** | gRPC 텐서 처리에서 400KB 텐서 전송이 **~10–15% 개선** |
| **임시 객체 재사용** | 루프 밖으로 변수 정의를 끌어올려 버퍼를 돌려 쓴다 |

> 웹서버 사례가 흥미롭다 — **미리 할당을 "더" 하는 것이 항상 이득은 아니다.** 200개를 잡아두던 것을 10개로 줄여서 7.5%를 얻었다. 과다 예약도 비용이다.

### 4.5 불필요한 일 피하기

#### Fast path
흔한 경우를 빠르게 하되 드문 경우를 크게 해치지 않는 구조. 예 — UTF-8 스캐너가 4바이트 배수만 처리하고 나머지는 느린 범용 루틴으로 넘기던 것을, **끝에 남은 단일 ASCII 바이트까지 처리**하도록 확장. 5바이트짜리 순수 ASCII 문자열이 더는 느린 경로로 빠지지 않는다.

#### Precompute
- 초기화 시점에 노드 속성을 **한 번만** 계산해 저장 (TensorFlow `NodeItem`의 `kernel_is_expensive`, `is_async`, `is_merge`)
- 256개짜리 룩업 테이블 미리 계산
- **조기 기각 필터** — 비싼 fingerprint 계산 전에 첫 바이트 배열 조회로 먼저 거른다

#### Defer
비싼 계산을 자주 도는 경로 밖으로 민다. 원문에서 가장 극적인 수치 —

```
XLA sharding_propagation.cc
  before: 조건 검사 전에 GetSubSharding() 호출
  after : 해당 operand 일 때만 호출

  CPU 43초 → 2초
```

#### Specialize
| 일반 코드 | 특화 코드 | 이득 |
|---|---|---|
| `sprintf` | 히스토그램 전용 출력 | **4배** |
| RE2 정규식 | 단순 prefix 매칭 | — |
| `StringPrintf` | IP 포맷팅에 `StrCat` | — |

#### Caching
fingerprint 기준으로 결과를 캐시해 큰 직렬화 데이터의 반복 파싱을 없앤다.

### 4.6 컴파일러를 돕기

> ⚠️ **프로파일이 문제를 보여줄 때만 하라.** 컴파일러는 대개 알아서 잘한다. 성능 임계 루틴은 **생성된 어셈블리를 직접 보라** — pprof가 소스와 디스어셈블리를 성능 데이터와 함께 보여준다.

- hot 함수에서 함수 호출 피하기 (프레임 셋업 비용 제거)
- slow-path를 **별도 tail-call 함수**로 분리
- 작은 데이터를 지역 변수로 복사해 **aliasing 가정을 없앤다**
- 아주 뜨거운 루프는 **손으로 언롤** — CRC32 계산을 4바이트 → **16바이트 단위**로

### 4.7 통계·로깅 비용

성능 문서가 잘 다루지 않는 축이다. **정보의 효용과 유지 비용을 저울질하라.**

| 전략 | 사례 |
|---|---|
| **쓸모없는 통계는 아예 버린다** | SelectServer의 알람·클로저 개수 통계 제거. 알람 설정이 **771 ns → 271 ns** |
| **샘플링** | 1/10 → **1/32**. 2의 거듭제곱 모듈러로 판정 비용까지 낮춘다 |
| **샘플된 것만 통계 유지** | 패킷 실행기 **224 ns → 85 ns (+62.0%)** |
| **지연 계산** | 할당·해제마다 갱신하지 말고, 훨씬 드물게 불리는 `Stats()`에서 계산 |
| **hot path 로깅 제거** | 할당기 hot path에서 로깅 제거, 로깅 활성 여부는 루프 밖에서 미리 판정 |

### 4.8 코드 크기

> **성능은 실행 속도만이 아니다.** 코드가 크면 컴파일·링크가 느려지고, 바이너리가 붓고, 메모리를 더 쓰며, **icache 압박과 분기 예측기 등 마이크로아키텍처 구조에 악영향**을 준다. 여러 곳에서 쓰일 저수준 라이브러리나 많은 타입으로 인스턴스화될 템플릿 코드라면 특히 중요하다.

| 기법 | 사례와 수치 |
|---|---|
| **널리 인라인되는 코드 다듬기** | `RETURN_IF_ERROR` **호출 지점마다 79바이트** 축소. 어떤 함수는 **125 → 77 바이트** |
| **신중한 인라인** | 바이너리 **12.2%** 감소 (8,814,545 → 7,740,233 바이트). 다른 사례에서는 큰 바이너리들이 **~0.5%** 감소 |
| **템플릿 인스턴스화 줄이기** | — |
| **컨테이너 연산 줄이기** | — |

### 4.9 병렬화와 동기화

| 기법 | 수치 |
|---|---|
| **병렬성 활용** | 4-way 병렬화로 토큰 인코딩 **~3.6배**. 항목별이 아니라 **배치 단위**로 나눠 병렬 실행 비용을 상쇄 |
| **락 획득 상각** | 여러 항목을 한 번의 락으로 |
| **임계 구역 짧게** | — |
| **샤딩으로 경합 감소** | 캐시를 **16-way 샤딩** → 멀티스레드 throughput **~2배**. 전제: 샤드 간 불변식이 없어야 한다 |
| **SIMD** | — |
| **false sharing 감소** | — |
| **컨텍스트 스위치 빈도 감소** | fiber 8192개 벤치마크에서 **wall-clock −69%** |
| **버퍼드 채널 파이프라이닝** | — |
| **lock-free** | RPC 채널 캐시(초당 수천 회 읽기, 드문 쓰기)에 lock-free 맵 → 탐색 latency **3–5%** 감소. ⚠️ 원자 변수 직접 조작은 위험하니 **상위 추상화를 선호** |

### 4.10 Protocol Buffer

> **가장 큰 단일 수치가 여기 있다.** 점 1000개를 채우고 Y좌표를 합산하는 코드를 protobuf에서 **C++ struct의 `std::vector`** 로 바꾸니 **20배** 빨라졌다.

```
name                old time/op   new time/op   delta
BenchmarkIteration  17.4µs ± 5%   0.8µs ± 1%    -95.30%  (p=0.000 n=11+12)
```

protobuf는 **전송·영속화에는 편리하지만 계산용 내부 표현으로는 비싸다**는 것이 요지다.

### 4.11 C++ 타입 선택

| 타입 | 용도 |
|---|---|
| `absl::flat_hash_map/set` | `std::map`·`std::unordered_map`보다 대체로 빠름. `__gnu_cxx::hash_map` → `flat_hash_map` 교체로 `BM_CodeToLanguage` **19.4 ns → 10.2 ns (−47.5%)** |
| `absl::btree_map/set` | 정렬 순회가 필요할 때 |
| `util::bitmap::InlinedBitVector` | 작은 정수 도메인의 집합 |
| `absl::InlinedVector` | 보통 원소가 적은 벡터 |
| `gtl::vector32` | 32bit 인덱스 벡터 |
| `gtl::small_map` / `small_ordered_set` | 원소가 적은 맵·집합 |
| `gtl::intrusive_list` | 노드 할당 없는 리스트 |
| **`absl::Status` / `StatusOr` 사용 제한** | 성공 경로에서도 **비용이 0이 아니다.** 의미 있는 에러 정보가 필요 없는 hot 루틴에서는 피할 것. 실제로 hot path에서 `StatusOr` 제거로 RPC 스택의 **14% CPU 회귀를 해소** |

### 4.12 Bulk operations

**항목을 하나씩이 아니라 여러 개를 한 번에 다뤄라.** `absl::flat_hash_map`이 대표 사례 — 여러 키의 해시 바이트 하나씩을 **SIMD 명령 하나로 동시에 비교**한다 (Swiss Table).

### 5.2 이 표에서 읽히는 것

> **① 가장 큰 이득은 "표현을 바꾸는 것"에서 나온다.** 20배(protobuf→struct), 21.5배(지연), 4배(특화) 모두 **더 잘 짜서**가 아니라 **다른 것을 쓰기로 해서** 얻었다. 미시 최적화는 대체로 10~30% 대에 머문다.
>
> **② 통계·로깅이 의외로 큰 항목이다.** 771→271 ns, 224→85 ns는 **기능이 아니라 계측 때문에** 나가던 비용이다. 성능 논의에서 자주 빠지는 축이다.
>
> **③ 그럼에도 저자들은 3~5%짜리를 함께 싣는다.** §2 통찰 2("1% 개선 20개")와 일관된 편집 방침이다. **작은 수치를 부끄러워하지 않는 것 자체가 이 문서의 주장**이다.

## 6. Key Takeaways

1. **"나중에 프로파일링하자"의 진짜 대가는 느린 코드가 아니라 평평한 프로파일이다.** 성능이 여기저기서 조금씩 새면 뚜렷한 hotspot이 없어 **어디서 시작할지조차 알 수 없다**. 저자들이 사전 고려를 주장하는 첫 번째 이유가 이것이다.

2. **처방은 "최적화하라"가 아니라 "기본값을 잘 고르라"다.** *"가독성·복잡도를 크게 해치지 않는다면 더 빠른 쪽을 고르라."* `std::vector` 대신 `InlinedVector`를 쓰는 정도는 **비지역적 복잡도를 만들지 않으면서** 출발선을 높인다.

3. **측정 전에 추정이 온다.** 코드가 없는 설계 시점에는 프로파일러가 무력하다. quicksort 예제에서 **지배 항이 메모리(7.5s)가 아니라 분기 예측 실패(75s)** 임을 코드 없이 알아낸 것이 추정의 값어치다. 이를 위해 **자기 시스템의 상위 연산 비용표**를 갖고 있어야 한다.

4. **가장 큰 이득은 표현을 바꾸는 데서 나온다.** 20배(protobuf→struct), 21.5배(계산 지연), 4배(특화)는 모두 "더 잘 짜기"가 아니라 **"다른 것을 쓰기"** 였다. 미시 최적화는 대체로 10~30%다. 프로파일이 평평하면 **미시 최적화가 아니라 콜스택 위쪽의 구조**를 봐야 하는 이유다.

5. **계측 비용은 기능 비용만큼 크다.** 알람 설정 771→271 ns, 패킷 실행기 224→85 ns는 전부 **통계 수집을 줄여서** 얻었다. 쓸모없는 통계는 버리고, 필요하면 샘플링하고, 갱신은 지연시켜라.

6. **성능은 실행 속도만이 아니다.** 코드 크기는 컴파일·링크 시간, 바이너리 크기, **icache 압박과 분기 예측기**에 영향을 준다. 널리 쓰이는 라이브러리·템플릿 코드에서 특히 그렇다.

7. **작은 개선을 부끄러워하지 말라 — 문서의 편집 방침 자체가 주장이다.** Knuth가 "12% 개선은 확립된 공학 분야에서 결코 사소하지 않다"고 했듯, 저자들은 3.3%짜리 CL도 20배짜리와 나란히 싣는다. **1% 짜리 20개면 상당한 폭**이고, 그 작업에는 **안정적이고 품질 좋은 마이크로벤치마크**가 전제다.

8. **범위를 명확히 알고 읽어야 한다.** 이 문서는 **단일 바이너리의 일반 튜닝**만 다룬다. 분산 시스템과 ML 하드웨어 성능은 "그 자체로 거대한 영역"이라며 명시적으로 제외한다.
