# §3.2 Flexible and Efficient Kernel Development with TileLang — 차근차근

V4 같은 복잡한 아키텍처(CSA + HCA + mHC + sliding window + attention sink + ...)는 **수백 개의 fused kernel** 을 요구한다. 이것을 어떻게 효율적으로 개발했는가에 대한 답.

---

## 1단계: 출발점 — Kernel 개발의 본질적 어려움

### 옵션 A — PyTorch ATen operator 만 사용
- 장점: 빠른 개발, 자동 미분
- 단점: 각 operator 마다 GPU 메모리 read/write → **수십~수백 ATen op 가 chained** 되면 매우 비효율
- V4 의 hybrid attention 은 한 layer 에 100+ ATen op 발생 → 비현실적

### 옵션 B — 직접 CUDA / Triton 작성
- 장점: 최대 성능
- 단점: 개발 시간이 model architecture 변경 속도를 못 따라감
- attention 구조가 매번 바뀔 때마다 처음부터 재작성

### 옵션 C — 중간 추상화 (DSL)
- TileLang, ThunderKittens, Triton, CUTLASS DSL 등
- 추상화 ↔ 성능 trade-off

V4 는 **TileLang 채택** [P21].

---

## 2단계: TileLang 이란?

### 핵심 아이디어 (Wang et al. 2026, [P21])

> "Pythonic 으로 GPU kernel 작성하되, **dataflow** 만 명시하면 컴파일러가 scheduling 결정"

### 세 가지 디자인 원칙
1. **Pythonic**: Python 생태계와 자연스럽게 통합
2. **Dataflow-centric**: 사용자는 dataflow 만 신경 쓰고 thread binding/layout/pipeline 은 컴파일러가 처리
3. **Composability**: kernel/primitives/scheduling 가 자유롭게 조합

### 코드 예시 (개념)
```python
@T.prim_func
def matmul(A, B, C):
    with T.Kernel(M//block_M, N//block_N) as (bx, by):
        # Tiling, layout, pipeline 등은 어노테이션으로 표현
        T.copy(A[bx*block_M:..., :], A_shared)
        T.copy(B[:, by*block_N:...], B_shared)
        T.gemm(A_shared, B_shared, C_local)
```

### 지원 하드웨어
- NVIDIA: H100 (TMA/WGMMA), A100, V100, RTX 시리즈
- AMD: MI250, MI300X
- 후속 확장: Apple Metal, NVIDIA CUTLASS DSL backend, Ascend NPU [P21]

## 3단계: V4 의 TileLang 활용 — 수백 개 kernel

### 활용 영역
- attention 변형 (CSA, HCA, sliding window, attention sink)
- MoE expert (Linear-1, Linear-2, SwiGLU)
- mHC (A,B,C 매핑 + Sinkhorn-Knopp)

### 효과
- "**수백 개 fine-grained ATen op → 소수의 fused kernel**" 로 줄임
- attention variant 검증 시 **빠른 prototyping** 가능
- production deployment 에서도 **CUDA 직접 작성과 동급 성능**

### 커뮤니티 협업
- V4 팀이 TileLang 커뮤니티에 적극 contribution
- 현재 → "더 agile, efficient, stable kernel development workflow" 형성

## 4단계: V4 가 추가한 두 가지 핵심 개선

### (a) Host Codegen — Invocation Overhead 제거

**문제**:
- 빠른 GPU kernel 일수록 **host-side overhead** 가 상대적으로 부각
- Python 으로 작성된 launch validation logic = **수십~수백 µs** per invocation

**V4 의 해결**:
- **Host Codegen**: host-side validation/marshaling 을 generated host code 로 이동
- TVM-FFI 기반의 compact calling convention + zero-copy tensor interop
- 결과: **CPU-side validation overhead 가 µs 단위로 감소**

```
Before: Python → 100 µs validation → kernel launch
After:  Generated C → 0.5 µs validation → kernel launch
```

→ small kernel 의 throughput 한계 해소.

### (b) SMT-Solver Assisted Formal Integer Analysis

**문제**:
- TileLang kernel 은 복잡한 tensor index 산술 포함
- Layout inference, memory hazard detection, bound analysis 등 컴파일러 pass 가 **integer expression 의 properties 를 증명** 해야 함
- 표준 컴파일러 분석은 보수적 → 많은 최적화 기회 놓침

**V4 의 해결**:
- **Z3 SMT solver** [P22] 를 TileLang algebraic system 에 통합
- 비선형 integer arithmetic (QF_NIA fragment) 표현 처리
- Integer Linear Programming (ILP) solver 로 표준 expression 처리
- Z3 의 비선형 추론으로 vectorization over variable shapes 같은 복잡 케이스 해결

→ 기존 TileLang 으로는 적용 못 한 advanced optimization 이 unlock.

## 5단계: 정확도와 재현성 우선

### Default 정책 — Accuracy First
- Fast-math optimizations **disabled by default**
- 정밀도 손실 가능 approximation 은 **opt-in** 으로 명시 (예: `T.__exp`, `T.__log`, `T.__sin`)
- Strict IEEE-754 가 필요하면: `T.ieee_fsqrt`, `T.ieee_fdiv`, `T.ieee_add`

### 비트 단위 재현성
- TileLang 의 algebraic simplification + lowering 규칙을 mainstream CUDA toolchain (NVCC) 과 align
- bit-level difference 발생할 transformation 회피
- `T.annotate_layout` 으로 evaluation/accumulation order 강제 지정 가능
- → CUDA 직접 작성한 reference 와 **bit-identical output**

### 결과
- Accuracy/reproducibility 보장하면서도 성능 손실 없음
- "Selectively relax numerical constraints for higher speed" 라는 knob 노출

## 6단계: 왜 TileLang 인가? (다른 DSL 과 비교)

| DSL | 특징 | V4 가 안 택한 이유 |
|---|---|---|
| **Triton** | OpenAI 의 Python DSL | Hopper TMA/WGMMA 자동 지원 약함 (당시 기준) |
| **CUTLASS DSL** | Tensor core 직접 제어 | scheduling 추상화 약함, 개발 속도 ↓ |
| **ThunderKittens** | 작은 tile 기반 | 다양한 하드웨어 backend 지원 약함 |
| **TileLang** | dataflow-centric + multi-backend | **모든 측면 균형** ✓ |

V4 paper:
> "balances development productivity with runtime efficiency, enabling rapid development while supporting deep, iterative optimizations within the same codebase."

## 정리 — §3.2 한눈에 보기

| 항목 | 기존 방식 | V4 (TileLang + 개선) |
|---|---|---|
| Kernel 개수 | 수백 개 ATen op | 소수 fused kernel |
| 개발 속도 | 느림 (직접 CUDA) | **빠름** (Pythonic DSL) |
| Host overhead | ~100µs / launch | **<1µs** (Host Codegen) |
| 컴파일러 분석 | 보수적 ILP | **Z3 SMT 추가** → 더 많은 최적화 unlock |
| 정밀도 | varies | **Strict IEEE-754 default**, opt-in fast-math |
| 비트 재현성 | 불가능 | CUDA reference 와 **bit-identical** |

**핵심 통찰**:
1. Trillion-scale 모델은 **수백 개 fused kernel** 이 필요 → 수동 CUDA 는 비현실적
2. **TileLang** 은 productivity 와 performance 의 sweet spot
3. **Host Codegen** + **Z3 SMT solver** 통합이 V4 의 차별 contribution
4. **Accuracy-first default** 가 production deployment 와 reproducibility 보장
