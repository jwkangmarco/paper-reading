# §3.1 Fine-Grained Communication-Computation Overlap in Expert Parallelism — 차근차근

V4 가 1.6T MoE 를 학습/서빙 가능하게 만든 시스템 핵심. **MoE 의 본질적 통신 비용을 어떻게 숨길까** 에 대한 답이다.

---

## 1단계: 출발점 — Expert Parallelism 의 본질

### MoE 학습의 분산 전략

trillion-scale MoE 에서 expert 파라미터를 다수 GPU 에 분산 = **Expert Parallelism (EP)**.

```
Token 1 → Expert 3 (GPU 5), Expert 7 (GPU 12)
Token 2 → Expert 1 (GPU 1), Expert 12 (GPU 20)
...
```

각 토큰이 서로 다른 GPU 의 expert 로 가야 함 → **All-to-All 통신** 필수.

### MoE forward 의 4 단계 (V4 paper §3.1)

```
1. Dispatch (All-to-All ↑):  토큰을 routing 결과대로 expert GPU 로 전송
2. Linear-1 (compute):       SwiGLU gate + up projection
3. Linear-2 (compute):       down projection
4. Combine (All-to-All ↓):   결과를 원래 GPU 로 복귀
```

→ 통신 2 번 + 계산 2 번이 sequential 하게 발생.

### 본질적 문제

- 토큰당 통신 양: 수십 KB
- 토큰당 계산 양: 수백 GFLOPs
- → **GPU compute 가 통신 대기로 idle** 시간 폭증
- 1.6T 모델, 1024 GPU 클러스터에서 통신 비중이 학습 시간의 30~50% 차지 가능

## 2단계: 전 단계 — Comet 같은 기존 접근 (Zhang et al. 2025)

### Naive 방법 (overlap 없음)
```
[Dispatch][Linear-1][Activation][Linear-2][Combine]
   ────→     ────→        ────→      ────→
  통신       계산           계산        통신
```
→ 4 단계 모두 sequential, GPU 자주 idle.

### Comet (Zhang et al. 2025, [P18])
```
시간축 →
Dispatch ────────                     Combine ──────
                  [Linear-1][Act][Linear-2]
```
- Dispatch 와 Linear-1 을 overlap
- Linear-2 와 Combine 을 overlap
- 이론상 1.42× speedup [P1 논문]

### Comet 의 한계
- **두 단계만 부분 overlap**, 나머지 통신은 여전히 노출
- Expert wave 분할 안 함 → 통신 끝나야 계산 시작 가능

---

## 3단계: V4 의 통찰 — 통신은 계산 안에 *완전히* 숨겨질 수 있다

### 핵심 관찰 (V4 paper §3.1)

> "within a single MoE layer, the **total time of communication is less than that of computation**"

→ 통신을 "병목" 으로 취급하지 말고, **계산 시간 안에 fully hidden** 시킬 수 있다.

수학적 조건:
```
계산 / 통신 = C/B ≤ V_comp / V_comm
```
- `C` = peak compute throughput
- `B` = interconnect bandwidth
- `V_comp / V_comm` = layer 의 계산량/통신량 비

V4-Pro 의 token-expert 쌍 비용:
- 계산: `6hd` FLOPs (SwiGLU gate + up + down)
- 통신: `3h` bytes (FP8 dispatch + BF16 combine)
- → `C/B ≤ 2d = 6144 FLOPs/Byte` 면 통신 완전 hide

→ 1 GBps 통신당 6.1 TFLOP/s 면 충분. 이 점을 넘으면 통신이 더 이상 bottleneck 아님.

## 4단계: V4 의 해법 — Wave-based Fine-grained EP

### Wave 분할 아이디어

Expert 들을 한 번에 처리하지 않고 **wave** 로 쪼갠다:

```
Wave 1: Expert 1, 2, 3 → Linear-1
Wave 2: Expert 4, 5, 6 → Linear-1
Wave 3: Expert 7, 8, 9 → Linear-1
```

각 wave 안에서:
- **Wave 1 의 통신이 끝나면 Wave 1 계산 시작**
- 동시에 **Wave 2 통신 시작**
- 계산과 통신이 완전 pipelined

### V4 의 EP 스케줄

```
Time →
Dispatch:  [W1]------[W2]------[W3]------
Compute :       [W1 L1+L2][W2 L1+L2][W3 L1+L2]
Combine :              ------[W1]------[W2]------[W3]
                       ↑ activation
```

- 모든 wave 가 dispatch / compute / combine 의 다른 stage 에서 동시 진행
- **Steady state 에서 GPU 가 idle 안 됨**

### 결과
- 이론 speedup: **1.92×** (V4 paper, vs Comet 1.42×)
- 실측: **1.5–1.73× over non-fused baselines** (NVIDIA H100 + HUAWEI Ascend NPU)
- RL rollout / latency-sensitive serving: **최대 1.96×**

## 5단계: MegaMoE — 단일 Mega-Kernel 구현

### Kernel Fusion 의 의의

V4 는 위 wave 스케줄을 **단일 CUDA mega-kernel** 로 구현:

```cuda
__global__ void MegaMoE(...) {
    // Warp group 1: Dispatch (All-to-All)
    // Warp group 2: Linear-1 (GEMM)
    // Warp group 3: Activation (SwiGLU)
    // Warp group 4: Linear-2 (GEMM)
    // Warp group 5: Combine (All-to-All)
    // → 모두 같은 kernel 내 다른 warp group 으로 동시 실행
}
```

### Fused 의 장점
- Kernel launch overhead 제거 (4~5 번이 1 번으로)
- Warp-level scheduling 으로 통신·계산이 GPU 내부에서 자유롭게 interleaved
- 메모리 사용량 ↓ (intermediate tensors 가 register/shared memory 에 머무름)

### Open-source
- **MegaMoE** 라는 이름으로 오픈소스 [V4 paper §3.1]
- DeepGEMM repo 의 PR #304: https://github.com/deepseek-ai/DeepGEMM/pull/304
- NVIDIA H100 + HUAWEI Ascend NPU 둘 다 지원

## 6단계: 하드웨어 vendor 에 대한 제언

V4 paper 가 §3.1 마지막에 **하드웨어 설계자들에게 보내는 제언** 4 가지:

### (a) Computation-Communication Ratio
- 무조건 bandwidth 만 늘리지 말고 **C/B = 6144 FLOPs/Byte** balance point 에 맞추라
- 이미 충분하면 silicon 을 추가 bandwidth 에 쓰는 게 의미 없음

### (b) Power Budget
- Mega-kernel 은 compute, memory, network 를 **동시 최대 부하**
- 전력 throttling 이 새 병목 → power headroom 확보 필요

### (c) Communication Primitives
- V4 는 **pull-based** (각 GPU 가 remote GPU 에서 데이터 읽음) 채택
- 이유: push 의 high notification latency
- 미래 하드웨어는 **low-latency cross-GPU signaling** 으로 push viable 하게

### (d) Activation Function
- SwiGLU 의 exponential/division 을 **저비용 element-wise** 로 교체 제안
- gate projection 제거하고 intermediate dim ↑ 가 더 효율적

→ V4 가 단순히 모델 paper 가 아니라 **co-design 제안서** 의 성격.

## 정리 — §3.1 한눈에 보기

| 단계 | 통신 hide 비율 | 메커니즘 |
|---|---|---|
| Naive sequential | 0% | 모두 노출 |
| **Comet** [P18] | ~40% | Dispatch↔L1, L2↔Combine 각각 부분 overlap |
| **V4 MegaMoE** | **~100%** | Wave 분할 + 단일 mega-kernel + 5-stage pipeline |

**핵심 통찰**:
1. MoE 의 통신 비용은 **본질적이지만 hideable**. C/B 비율이 충분하면 fully overlap 가능
2. **Wave-based scheduling** 이 핵심. expert 를 batch 단위가 아닌 wave 단위로 처리
3. **Single mega-kernel** 로 4~5 개 stage 를 융합 → kernel launch + memory traffic 제거
4. **하드웨어와의 co-design** — 단순 SW 최적화가 아니라 미래 칩 설계에까지 영향
