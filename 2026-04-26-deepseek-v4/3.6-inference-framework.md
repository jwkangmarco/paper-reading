# §3.6 Inference Framework — 차근차근

V4 의 hybrid attention (CSA + HCA + sliding window) 와 1M context 를 **실제 production 에서 서빙** 가능하게 만든 인프라. **§2.3 의 architecture 가 §3.6 의 KV cache 관리 없이는 deploy 불가**.

---

## 1단계: 출발점 — KV Cache Management 의 표준

### PagedAttention (vLLM, [P40])

LLM 서빙의 표준이 된 KV cache 관리 방식 (Kwon et al. 2023):

**핵심 아이디어**: OS 의 virtual memory paging 을 KV cache 에 적용.
- KV cache 를 **고정 크기 block** (e.g., 16 token) 으로 분할
- Block 들을 GPU 메모리 어디든 배치 (contiguous 불필요)
- **Block table** 이 logical → physical 매핑 유지

**효과**:
- KV cache 메모리 낭비 60~80% → 4% 미만
- shared prefix 효율적 sharing
- variable-length request batch 가능

→ V3 까지의 표준 KV cache 관리 방식.

---

## 2단계: V4 의 도전 — Hybrid Attention 이 PagedAttention 의 가정을 깬다

### PagedAttention 의 가정

PagedAttention 의 디자인은 **모든 layer 가 단일 attention 형태** 가정:
- 모든 layer 가 같은 KV 형태와 크기
- 단일 cache policy

### V4 의 hybrid attention 이 가정을 깸

V4 의 layer 마다 KV 가 다름 (§2.3 참고):

| Layer 종류 | KV 형태 |
|---|---|
| **Sliding Window only** (첫 1~2 layer) | uncompressed, last n_win=128 tokens |
| **CSA layer** | compressed (m=4), + sliding window + indexer KV |
| **HCA layer** | heavily compressed (m'=128), + sliding window |

### 문제점

1. **Diverse cache policy** — sliding window 의 LRU eviction 과 CSA/HCA 의 long-term retention 이 다름
2. **High-performance attention kernel 의 alignment 요구** — block size 가 m, m' 의 lcm 에 align 해야 효율
3. **압축 단위가 m token** → tail 토큰이 m 미만이면 **buffer 에 보관, 압축 미완**

### vLLM 의 부분 해결책 [P41]
- vLLM Hybrid KV Cache Manager: full attention + 1 종 의 효율 attention 까지 지원
- **3 종 이상의 attention 은 미지원** → V4 와 안 맞음

---

## 3단계: V4 의 해법 (§3.6.1) — Heterogeneous KV Cache Layout

### 두 컴포넌트 분리

V4 는 KV cache 를 **두 종류 storage 로 분리** (V4 paper Figure 6):

**(a) State Cache** — request 별 fixed-size:
- SWA (sliding window attention) KV
- CSA/HCA 의 **압축되지 않은 tail tokens** (m 미만이라 압축 미완)
- 모든 request 가 자기 fixed-size block 을 갖고 SWA segment + uncompressed tail 보관

**(b) Classical KV Cache** — block 단위:
- CSA 의 압축된 KV
- HCA 의 압축된 KV
- CSA 의 indexer KV (separate dimensional space)

### 핵심 design choice

**State cache 를 sequence-state 로 취급**:
> "we adopt an alternative cache management mechanism. Since SWA is designed to enhance performance under a limited KV cache size, it is reasonable to treat it, along with the uncompressed tail tokens from the compression branch, as a **state-space model**."

- SWA + uncompressed tail = **현재 sequence position 에 dependent**, fixed-size pool 로 처리
- 미리 pool 할당, sequence 마다 dynamic assign
- → eviction policy 단순화

**Classical cache 의 block size 정렬**:
- block 당 token 수 = `lcm(m, m')` 의 multiple
- 예: m=4, m'=128 → lcm=128 의 multiple
- 결과: CSA k_1 = lcm/m = 32 개 압축 tokens, HCA k_2 = lcm/m' = 1 개 압축 token per block

### Sparse Attention Kernel Co-design

기존 PagedAttention 의 sparse attention kernel:
- **block 당 fixed 토큰 수** 가정
- 다양한 layer type (CSA k_1=32, HCA k_2=1) 에서 효율 ↓

V4 의 solution:
- **High-performance sparse-attention kernel** 자체 개발
- variable tokens per block 을 **performance 손실 없이** 처리
- KV cache layout + kernel 의 **co-design** 으로 cache line alignment 등 보장

## 4단계: §3.6.2 On-Disk KV Cache Storage — Shared-Prefix 대응

### Motivation

LLM 서빙에서 흔한 패턴:
- 같은 long system prompt + 다른 user query
- → prefix 의 KV cache 를 **재계산하면 GPU 시간 낭비**
- 1M context 면 prefill 만 수십 초 ~ 수 분

### V4 의 해법 — On-disk caching

**압축된 KV (CSA, HCA)**:
- 모든 압축 entry 를 disk 에 저장
- prefix hit 시: prefix 까지의 압축 KV 를 disk 에서 read
- tail incomplete block 만 recompute (uncompressed 가 아닌 compressed 만 저장이라)

**SWA KV** (uncompressed):
- 압축 KV 보다 **8× 더 큼** (모든 layer 에 존재 + uncompressed)
- SSD 기반 storage 에 그대로 저장하면 비효율적
- → **3 가지 전략** 제시 (deployment 마다 선택)

### SWA Cache 의 3 가지 전략

**(a) Full SWA Caching**:
- 모든 token 의 SWA KV 저장
- prefix hit 시 last n_win 개만 read 하면 됨 → **0 redundancy**
- 단점: 매 request 마다 작은 일부만 read → SSD I/O pattern 비효율 (대부분 unused)

**(b) Periodic Checkpointing**:
- **매 p 토큰마다** SWA KV 저장
- prefix hit 시 가장 가까운 checkpoint 부터 tail 만 recompute
- p tunable: 작으면 storage ↑, 크면 recompute ↑
- → **on-demand trade-off**

**(c) Zero SWA Caching**:
- SWA KV 전혀 안 저장
- prefix hit 시: 캐시된 CSA/HCA KV 로 last `n_win · L` 개 token 만 recompute
- L = layer 수
- 가장 storage-efficient, 그러나 recompute 가장 많음

V4 는 deployment 시나리오에 맞게 **세 전략 중 선택**.

## 5단계: 추론 효율의 정량 결과 (§2.3.4 와 연결)

V4 의 inference framework 가 implementation 한 efficiency:

| 항목 | V3.2 | V4-Pro (1M) | V4-Flash (1M) |
|---|---|---|---|
| Single-token FLOPs | 100% | 27% | 10% |
| KV cache 크기 | 100% | 10% | 7% |

추가:
- BF16 GQA8 baseline 대비 KV cache **~2%**
- Indexer 의 FP4 (§3.4) → 양자화로 더 빠름
- On-disk caching → shared-prefix 시나리오에서 prefill 거의 zero-cost

## 6단계: 다른 시스템과의 비교

| 시스템 | KV 관리 | Hybrid attention 지원 | 1M context |
|---|---|---|---|
| **vLLM (PagedAttention)** [P40] | block 기반 paging | full attn + 1 종만 | 부분 지원 |
| **vLLM (Hybrid KV Manager)** [P41] | 위 확장 | 2 종까지 | 부분 지원 |
| **Jenga** [P42] | hybrid attention 일반화 | ✓ | 부분 지원 |
| **Hymba** [P43] | 특정 hybrid 구조 | 특정 케이스 | 부분 지원 |
| **V4 inference framework** | **state cache + classical cache 분리** | ✓ (3+ 종 가능) | **완전 지원** |

V4 가 **"3 종 이상 hybrid + 1M context + on-disk shared prefix"** 라는 가장 어려운 조합에 대한 답을 제시.

## 정리 — §3.6 한눈에 보기

| 도전 | V4 의 해법 |
|---|---|
| 다양한 attention type 의 KV diversity | **State cache + Classical cache 분리** |
| Sliding window 의 LRU eviction | State cache 의 **fixed-size pool** + sequence-specific assignment |
| CSA/HCA 의 압축 미완 tail | State cache 가 uncompressed tail 도 함께 보관 |
| Block size alignment | **`lcm(m, m')` multiple** 로 block 정렬 |
| Sparse attention kernel | KV layout + kernel co-design (variable tokens per block 지원) |
| Shared-prefix 재계산 | **On-disk KV cache** (CSA/HCA: 모두 저장, SWA: 3 가지 전략) |

**핵심 통찰**:
1. **PagedAttention 의 single-attention 가정이 V4 의 hybrid 에서 깨짐** → 새로운 cache layout 필요
2. **State cache vs Classical cache 분리** 가 핵심 architectural decision — sequence-state 로 취급할 부분과 block-cache 할 부분의 명확한 구분
3. **lcm(m, m') 정렬** 같은 detail 이 sparse attention kernel 효율의 결정타
4. **SWA on-disk 의 3-strategy** 는 storage/compute trade-off 의 구체적 예 — deployment 별 최적 선택
5. **§2.3 architecture (CSA/HCA) 와 §3.6 framework 는 한 몸** — KV management 없이는 1M context 서빙 불가능
