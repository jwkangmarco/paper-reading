# §3.3 High-Performance Batch-Invariant and Deterministic Kernel Libraries — 차근차근

V4 의 가장 "조용한" 그러나 중요한 contribution 중 하나. **재현성과 디버깅 가능성** 을 위해 결정론적·batch-invariant 커널을 설계한 이야기.

---

## 1단계: 출발점 — LLM 추론은 사실 비결정적이다

### 충격적 사실 (Thinking Machines Lab, 2025 [P26])

같은 prompt, 같은 weights, 같은 sampling seed 로 LLM 을 두 번 부르면 **출력이 다를 수 있다**.

이유 1: **Floating-point non-associativity**
```
(a + b) + c ≠ a + (b + c)    # 부동소수점에서 일반적으로 성립
```

이유 2: **Batch 크기에 따라 reduction 순서 변함**
- batch=1 일 때와 batch=32 일 때 GPU kernel 이 **다른 reduction tree** 사용
- → **같은 입력이라도 batch 위치에 따라 출력이 달라짐**

### 왜 문제인가
- 학습 시: loss spike 디버깅이 거의 불가능 (재현 안 됨)
- RL: rollout reproducibility 는 정확한 학습의 전제
- Production: 같은 query 가 시간마다 다른 답
- 과학적 이유: 모든 결과가 검증 불가

### 기존 frameworks 의 입장
- vLLM, SGLang, TensorRT 등: **performance 우선**, determinism 양보
- 일부 옵션 (`torch.use_deterministic_algorithms(True)`) 있지만 **수십% 느려짐**

---

## 2단계: "Batch Invariance" 정의

### Definition (Thinking Machines Lab, [P26])

> "어떤 token 의 출력이, **batch 안에서의 위치/batch size 에 무관** 하게 bitwise identical"

### 왜 batch invariance ⊆ determinism?

- Batch invariance 가 보장되면, batch=1 처리 결과 = batch=N 처리 결과 (해당 token에 대해)
- 모든 reduction 이 같은 algorithm 으로 처리되므로 **자동으로 결정론적**

V4 는 batch invariance 를 핵심 디자인 목표로 삼았다.

---

## 3단계: 도전 1 — Attention Kernel 의 Batch Invariance

### 문제: Split-KV 방법 [P27]

**기존 표준 (FlashAttention 등)**:
- 한 sequence 의 attention 을 **여러 SM (Streaming Multiprocessor)** 에 분산
- 각 SM 이 KV 의 일부를 처리 후 reduction
- → **SM 간 reduction order 가 batch size 에 따라 달라짐** = batch invariance 깨짐

### V4 의 해결 — Dual-Kernel Strategy

**Kernel 1 (single-SM per sequence)**:
- 한 sequence 의 attention 을 **단일 SM 에서 완결** 처리
- Reduction 이 SM 내부에서만 발생 → 결정론적
- 단점: **Wave-quantization** 문제 발생 (마지막 wave 가 부분 채워짐 → SM idle)

**Kernel 2 (multi-SM with deterministic reduction)**:
- 마지막 partially-filled wave 만 multi-SM 사용
- 단, **reduction order 를 Kernel 1 과 동일하게** 설계
- distributed shared memory (Hopper 의 thread-block cluster) 로 SM 간 데이터 교환 [P28]

**결과**:
- 두 kernel 의 출력이 **bitwise identical**
- 일반 wave 는 Kernel 1 (full throughput), tail 만 Kernel 2 (latency 흡수)
- **Batch-invariant decoding 의 overhead 가 negligible**

## 4단계: 도전 2 — Matrix Multiplication 의 Batch Invariance

### 문제: cuBLAS

- NVIDIA 의 표준 cuBLAS: batch invariance 보장 안 함
- 작은 batch size 에서 **split-K** [P29] 기법 사용 (성능을 위해 K 차원으로 GEMM 분할)
- → split-K 는 reduction order 변경 → 결정론 깨짐

### V4 의 해결
- **DeepGEMM** [P30] 으로 cuBLAS 교체
- split-K 포기 + 다양한 최적화로 standard split-K 와 동급 또는 우수한 성능 달성
- 일부 시나리오에서는 약간 성능 손해 → 재현성과 trade-off

---

## 5단계: Determinism — Backward Pass 의 추가 도전

### 문제: AtomicAdd 의 비결정성

GPU 의 `atomicAdd` 는 여러 thread 가 같은 메모리 위치에 더할 때 사용:
- **순서가 비결정적** → 부동소수점 non-associativity 와 결합 시 결과 매번 달라짐
- 주로 backward pass 에서 발생 (gradient accumulation)

### V4 의 해결 — 영역별 대응

**(a) Sparse Attention Backward**
- KV token 의 gradient 누적에 atomicAdd 사용 → 결정론 깨짐
- V4: 각 SM 에 별도 accumulation buffer 할당
- 모든 SM 끝나면 **전역 결정론적 합산** 으로 통합

**(b) MoE Backward**
- 여러 SM 이 다른 rank 의 같은 buffer 에 동시 write
- V4: rank 내부에서 **token order pre-processing** + **buffer isolation** across ranks
- → EP send 결과와 MoE backward accumulation order 둘 다 결정론적

**(c) mHC 의 Matrix Multiplication**
- mHC 의 출력 차원이 24 (매우 작음) → small batch 에서 split-K 강제 사용
- naive split-K = 비결정적
- V4: 각 split 결과를 **별도 출력 후 후속 deterministic reduction kernel** 에서 합산
- 성능과 결정론 둘 다 유지

## 6단계: 비용과 보상

### 비용
- Split-KV 포기로 **wave-quantization** 발생 (Kernel 2 로 우회)
- Split-K 포기로 **일부 GEMM 성능 손해**
- AtomicAdd 회피로 **추가 buffer 메모리**

### 정량 (V4 paper §3.3)
- 전체적으로 **deterministic kernel 의 overhead 는 negligible** (특히 Kernel 1 의 dominant case)
- 비결정론적 baseline 대비 일부 시나리오에서 ~10~20% 손해 (worst case)

### 보상
- **학습 디버깅** 가능: loss spike 의 numerical root cause 추적
- **RL 재현성**: rollout 이 결정론적이라 알고리즘 비교가 정확
- **Production reproducibility**: 같은 query 같은 결과
- **Pre/Post-training/Inference bitwise alignment**: 모든 stage 가 동일 동작

---

## 7단계: 왜 V4 가 이걸 했나? (motivation)

### Loss Spike 디버깅의 중요성
V4 paper §4.2.3 에 의하면:
> "We encountered notable instability challenges during training. ... rollbacks could only temporarily restore the training state, ... they proved inadequate as a long-term solution."

→ Trillion-scale 학습에서 loss spike 는 unavoidable.
- **결정론적 학습** 이면 numerical anomaly 의 정확한 원인 추적 가능
- → Anticipatory Routing, SwiGLU Clamping 같은 stability fix 를 발견할 수 있었음

### RL/OPD 의 요구
V4 의 post-training 은 RL 과 OPD 모두 활용 (§5):
- RL rollout 이 비결정적이면 algorithm comparison 불가
- OPD 의 teacher logit 도 학습 시점마다 달라지면 재현 안 됨

→ 결정론은 **production 만이 아니라 R&D 자체에 필수**.

### Thinking Machines Lab 의 영향 [P26]
- 2025년 Thinking Machines Lab 이 batch-invariant operator 라이브러리 공개
- SGLang 등이 곧이어 채택
- V4 도 같은 사상 위에서 더 광범위하게 (모든 backward 까지) 확장

## 정리 — §3.3 한눈에 보기

| 영역 | 문제 | V4 의 해법 |
|---|---|---|
| **Attention forward** | Split-KV 가 SM 별 reduction order 다름 | **Dual-kernel** (single-SM + multi-SM with same order) |
| **Matrix multiplication** | cuBLAS 의 split-K | **DeepGEMM** 으로 split-K 포기 |
| **Sparse attn backward** | atomicAdd 비결정 | SM 별 buffer + 전역 결정론적 reduction |
| **MoE backward** | rank 간 동시 write | token order pre-processing + buffer isolation |
| **mHC matmul (dim=24)** | 작은 dim 강제 split-K | 분할 후 별도 deterministic reduction kernel |

**핵심 통찰**:
1. **Batch invariance ⊆ Determinism** — 더 강한 보장이지만 같은 mechanism 으로 달성
2. **Floating-point non-associativity** 가 비결정성의 근본 원인 → reduction order 통일이 핵심
3. **Wave-quantization** 등의 부작용을 dual-kernel, deterministic reduction 등으로 흡수
4. **R&D productivity** (디버깅, RL reproducibility) 가 motivation, production 부산물
5. 성능 trade-off 가 있지만 **학습 안정성 발견에서 더 큰 이득**
