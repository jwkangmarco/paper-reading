# §3.5 Training Framework — 차근차근

V4 의 새 architecture (mHC, Muon, hybrid attention) 를 trillion-scale 로 학습 가능하게 만든 system 통합 작업. **§2 의 모델 변경이 §3.5 의 인프라 적응 없이는 학습 불가능했다**.

---

## 1단계: 출발점 — V3 의 baseline framework

V4 는 V3 의 학습 framework 를 **상속**:
- Pipeline parallelism (PP) — DualPipe 1F1B 스케줄
- Tensor parallelism (TP)
- Expert parallelism (EP)
- ZeRO Optimizer State Sharding [P17]
- Mixed precision (FP8/BF16)

→ 그러나 V4 의 새 component 들이 **전부 표준 framework 와 충돌**:
1. **Muon optimizer** ↔ ZeRO 가정 위반
2. **mHC** ↔ residual width 변화로 메모리·통신 ↑
3. **CSA/HCA** ↔ context parallelism 의 sequence partitioning 가정 위반
4. **세밀한 activation checkpointing 필요** ↔ 표준 module-level 부적합

→ §3.5 는 이 4 가지 충돌을 풀어낸 이야기.

---

## 2단계: §3.5.1 Muon × ZeRO 의 충돌

### ZeRO 의 가정

ZeRO [P17] 의 핵심 아이디어:
- AdamW 의 optimizer state 가 weight 보다 ~2× 큼
- → state 를 rank 별로 partition (sharding)
- 각 rank 가 자신의 partition 만 update

### Muon 의 요구사항
- Muon 은 **full gradient matrix 가 필요** (Newton-Schulz iteration 위해)
- Sharding 시 partial matrix 만 가지면 NS iteration 불가능

### V4 의 해결 — Hybrid ZeRO Strategy

**Dense parameters**:
- ZeRO size 에 **상한** 두기
- **Knapsack algorithm** 으로 parameter matrix 들을 rank 에 분배 (균형)
- 각 rank 는 평균 5 개 이하의 matrix 보유 → padding overhead < 10%
- ZeRO size 가 너무 크면: **redundant compute** (extra DP group 들에서 같은 update 반복) — 메모리 vs 연산 trade

**MoE parameters**:
- 각 expert 를 독립 단위로 처리
- 모든 expert 의 down/up/gate projection 을 flatten + concat
- → padding 으로 균등 분배
- Expert 수가 많아 ZeRO size 제한 불필요

**Newton-Schulz batching**:
- 같은 shape 의 consecutive parameter 를 **자동 merge**
- NS iteration 을 **batched matrix multiplication** 으로 실행 → GPU 효율 ↑
- Bf16 에서도 NS 안정 발견 → BF16 로 stochastic round 후 reduce-scatter
  - **통신 양 절반**
  - all-to-all 후 local FP32 sum → 정확도 보존

---

## 3단계: §3.5.2 mHC 의 메모리·통신 폭증

### 기본 cost
mHC 는 residual stream 을 `n_hc=4` 배 확장 → **활성화 메모리 4×, pipeline 통신 4×**.

### 완화 전략

**(a) Fused kernel for mHC**
- A_l, B_l, C_l 매핑 + RMSNorm + dynamic/static 합성을 **단일 kernel** 로 융합
- intermediate tensor 가 register/shared memory 에 머무름

**(b) Selective recomputation**
- **재계산할 것**: hidden state 사이의 **간단한** intermediate (RMSNorm 출력 등)
- **재계산 안 할 것**: compute-intensive 연산 (Sinkhorn-Knopp 결과)
- → balance: 메모리 절감 vs 연산 cost

**(c) DualPipe 1F1B 스케줄 조정**
- mHC 의 추가 pipeline 통신을 흡수하도록 1F1B 를 미세 조정
- 일부 mHC operation 을 PP stage 와 **concurrent execute**

### 결과
> "constrain the wall-time overhead of mHC to **only 6.7%** of the overlapped 1F1B pipeline stage"

→ 4× 활성화 부하를 6.7% 로 흡수.

## 4단계: §3.5.3 Context Parallelism × Compressed Attention 의 충돌

### Context Parallelism (CP) 기본
- 1M sequence 를 여러 GPU 에 partition (sequence 차원)
- 각 rank 는 자기 분량 `s` token 보유
- attention 시 ring-style 로 KV 교환 [P36]

### CSA/HCA 가 만드는 새 문제
- 학습 sample 이 **여러 sequence 를 packed** (일반적 packing)
- 각 sequence 는 m (또는 m') 단위로 압축
- → 압축된 KV 길이가 **균일하지 않고 rank 마다 다름** (s/m 미만일 수 있음)
- 게다가 압축은 m 개 consecutive KV 필요 → **CP boundary 를 가로지를 수 있음**

### V4 의 2-stage 통신

**Stage 1**:
- 각 rank `i` 가 자신의 마지막 m 개 uncompressed KV 를 rank `i+1` 로 전송
- Rank `i+1` 은 자기 데이터 + 받은 데이터로 **압축 수행**
- 결과: `s/m + 1` 개 압축 entry (일부 padding)

**Stage 2**:
- All-gather across CP ranks
- 모든 rank 가 압축된 KV 의 전체 길이 (`cp_size · s/m`) 보유
- **Fused select-and-pad operator** 로 padding 제거 + concat

**CSA top-k selector** 는 visible KV indices 명시 → boundary 처리 자동.

→ 결과: CP 가 1M 학습 가능, 압축 attention 과 호환.

## 5단계: §3.5.4 Tensor-Level Activation Checkpointing

### 기존 방식의 한계

**Module-level checkpointing** (PyTorch `torch.utils.checkpoint` [P37]):
- 단위가 module (layer, block) → 너무 거침
- 일부 tensor 만 keep / 일부만 recompute 가 불가능
- → 메모리 vs recompute cost trade-off 가 **suboptimal**

**Manual fwd/bwd**:
- Layer 의 fwd/bwd 를 직접 작성, 정밀 제어
- 단점: autograd framework 잃음 → 개발 복잡성 폭증

### V4 의 Tensor-level 접근

**아이디어**: Module 단위가 아니라 **tensor 단위** 로 keep / recompute 를 결정.

**구현**:
1. **PyTorch TorchFX** [P38] 로 forward 의 full computation graph 를 trace
2. 각 annotated tensor 마다 **backward traversal** 로 recomputation 에 필요한 **minimal subgraph** 추출
3. 이 subgraph 들을 backward logic 안에 삽입

**효과**:
- 개발자는 forward 만 작성 + tensor 단위 annotation
- Framework 가 자동으로 recomputation graph 생성
- **Manual implementation 대비 추가 overhead 없음**

### 추가 최적화
- Recomputed tensor 가 annotated tensor 의 storage pointer 재사용 (GPU memory copy 없음)
- Storage pointer tracking 으로 reshape 결과 같은 shared-storage tensor 의 recomputation 자동 dedupe
- → 개발자가 low-level memory 를 신경 쓸 필요 없음

## 6단계: 통합 결과 — Trillion-Scale 학습의 안정성

V4 paper §3.5 가 강조:

> "In training DeepSeek-V4, we **inherit this robust foundation** while introducing several key innovations to accommodate its novel architectural components — specifically the Muon optimizer, mHC, and the hybrid attention mechanism — while maintaining high training efficiency and stability."

= V4 의 system 변경은 모두 **§2 의 architecture 변경을 enabling 하는 것**.

### 핵심 패턴
- **Muon × ZeRO**: hybrid sharding strategy
- **mHC × pipeline**: fused kernel + selective recompute + 1F1B 조정
- **CSA/HCA × CP**: 2-stage 통신
- **Activation memory**: tensor-level checkpointing

→ 각 architecture 결정이 system level 에서 **non-trivial 한 통합 작업** 을 요구. 둘은 따로 떼어 평가 불가.

---

## 정리 — §3.5 한눈에 보기

| 컴포넌트 | 충돌 | V4 의 해결 |
|---|---|---|
| **Muon** | full gradient 필요 ↔ ZeRO sharding | Hybrid sharding (knapsack + redundant compute) |
| **Muon NS** | per-param NS iteration 비효율 | Auto-batching 같은 shape param + BF16 stochastic round |
| **mHC** | 활성화 메모리 4× | Fused kernel + selective recompute + 1F1B 조정 → 6.7% overhead |
| **CSA/HCA × CP** | 압축 단위가 rank boundary 가로지름 | 2-stage 통신 (rank 간 m KV 전달 + all-gather) |
| **Memory** | module-level checkpointing 너무 coarse | Tensor-level checkpointing via TorchFX trace |

**핵심 통찰**:
1. **새 architecture 는 기존 framework 와 항상 충돌** — V4 는 4 가지 비-trivial 통합 작업
2. **Hybrid 전략이 패턴**: 하나의 strategy 가 모든 case 를 cover 못 함. dense/MoE/CP/normal layer 마다 다른 처리
3. **ZeRO size 상한** (Muon 위해), **mHC overhead 6.7%** (recompute 균형) 같은 정량적 trade-off 가 핵심
4. **TorchFX 활용** → 개발 productivity 와 메모리 효율의 sweet spot
5. §2 architecture 와 §3 system 은 **동전의 양면** — 분리 평가 무의미
