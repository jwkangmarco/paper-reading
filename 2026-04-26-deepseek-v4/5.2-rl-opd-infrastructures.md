# §5.2 RL and OPD Infrastructures — 차근차근

V4 의 post-training 새 pipeline (specialist + OPD) 을 실제로 돌릴 수 있게 만든 인프라. **§5.1 의 OPD 가 §5.2 의 인프라 없이는 실현 불가능**.

---

## 1단계: 출발점 — V3.2 의 Post-training 인프라

V4 는 V3.2 의 post-training 인프라를 **상속**:
- Distributed training stack (§3.5 의 framework)
- Auto-regressive sampling rollout engine
- 표준 RLHF / RL pipeline

### 그러나 V4 의 새 요구사항이 충돌

1. **OPD with 10+ teachers** — teacher weight 가 trillion-scale, GPU 메모리에 다 못 올림
2. **Full-vocabulary KL** — vocab 크기 128K, naive 구현 시 메모리 폭발
3. **Million-token context RL** — 1M context 의 rollout 데이터 처리 / 분산
4. **Agentic tool-use** — 다양한 sandbox 환경 (function call, container, microVM 등) 필요
5. **Preemption tolerance** — GPU cluster 의 task 우선순위로 인한 중단 처리

→ §5.2 가 이 5 가지를 풀어낸 이야기.

## 2단계: §5.2.1 FP4 Quantization Integration

### Motivation
- §3.4 의 FP4 QAT 가 base 학습에서 적용됨
- Post-training (RL rollout, OPD inference) 에서도 FP4 활용해 가속·메모리 절감

### V4 의 적용
- **Rollout 과 inference forward pass: 직접 FP4 weight 사용**
- **Training forward (backward 동반)**: FP4 quantize 시뮬 + lossless FP4→FP8 dequant (§3.4)
- → 동일 framework, 동일 stage 모두 FP4 활용

### 효과
- Memory traffic ↓ → sampling latency ↓
- 같은 GPU 클러스터에서 더 많은 rollout 동시 진행 가능
- → RL/OPD 의 effective throughput 향상

## 3단계: §5.2.2 Efficient Teacher Scheduling for Full-Vocabulary OPD — 핵심 도전

### 문제 1 — Teacher weight 의 메모리 부담

10+ teacher × trillion params = **GPU 메모리에 모두 적재 불가**.

### V4 의 해결 — Centralized Distributed Storage

**Teacher weight 를 별도 storage 시스템에 offload**:
- 모든 teacher 가중치를 centralized distributed storage 에 저장
- Forward pass 시 **on-demand load** (ZeRO-like sharding)
- I/O 와 DRAM 부담 분산

### 문제 2 — Full-vocabulary logit 의 메모리 폭발

**Naive 구현**:
```
Teacher logit shape: [batch, seq_len, vocab_size]
                   = [B, 1M, 128K]
                   = 메모리 수백 GB ~ TB
```
- 모든 teacher × 모든 token × 모든 vocab → **저장 불가**
- 심지어 disk 에 spool 해도 비효율

### V4 의 해결 — Caching Last-Layer Hidden States

```
일반:
  Teacher Forward → Last hidden → Prediction Head → Logits → KL

V4:
  Teacher Forward → Last hidden 만 cache  ← teacher weight unload
                    ↓ 학습 시
                    Prediction Head 만 다시 통과 → Logits → KL
```

**구체 흐름** (V4 paper §5.2.2):
1. Teacher forward pass: last-layer hidden state 만 centralized buffer 에 cache
2. Training time: hidden state 를 retrieve → **prediction head 만 통과** → logit 재구성 → KL 계산
3. **Recomputation overhead 매우 작음** (prediction head 만)
4. 메모리 부담은 logit 대신 hidden 만 보관 (vocab 차원 → hidden dim 차원, **128K → 7K 절감**)

### 문제 3 — Teacher prediction head 의 GPU 메모리

- Teacher 가 N 개라면 **N 개 prediction head 동시 적재 시 GPU 부족**

### V4 의 해결 — Teacher-Indexed Sample Ordering

> "we order training samples by teacher index during data dispatching"

- 같은 teacher 의 sample 을 **연속 처리**
- → **mini-batch 당 teacher head 1 개만 GPU memory 유지**
- 다른 teacher 의 head 는 background 로 async load/offload

### 문제 4 — KL 계산의 GEMM 비용

- Full-vocab KL = `Σ p_teacher · log(p_teacher / p_student)` over 128K vocab
- naive 구현은 비효율적

### V4 의 해결 — Specialized TileLang Kernel

> "the exact KL divergences between teacher and student logits are computed using a specialized TileLang kernel, which accelerates the computation and curtails dynamic memory allocation"

- §3.2 의 TileLang 활용
- KL 계산만을 위한 fused kernel
- → 표준 PyTorch 대비 substantial speedup

## 4단계: §5.2.3 Preemptible and Fault-Tolerant Rollout Service

### Motivation

GPU cluster 의 현실:
- High-priority task (긴급 학습 등) 가 들어오면 **언제든 preemption 가능**
- 대규모 GPU cluster 는 **하드웨어 failure 일상적**

### 기존 방식의 비효율
- preemption 시 미완 generation request 폐기 → 전체 다시 generate
- 또는 length bias 도입 (짧은 응답이 더 많이 생존, **알고리즘 incorrectness**)

### V4 의 해결 — Token-Granular Write-Ahead Log (WAL)

**WAL 사상**:
- Database 의 WAL 처럼 모든 token 을 즉시 disk 에 append
- Generation request 마다 별도 WAL

**동작**:
```
Request 진행 중 → 매 token 마다 WAL append
   ↓ Preemption 발생 ← 인계 GPU 자원 release, KV cache save
   ↓ Resume
   WAL 의 토큰 + 저장된 KV cache 로 decoding 재개
   ↓ Hardware error 시
   Persisted WAL 의 토큰으로 prefill 재실행 → KV cache 재구성
```

### 왜 fresh re-generation 이 incorrect 한가?
- 짧은 response 가 interruption 보다 일찍 끝나 살아남음
- → **length bias** 누적 → 모델이 짧은 응답에 편향
- 결정론적 sampling (§3.3) + same seed 면 우회 가능하지만 **WAL 이 더 효율적**

### 효과
- Preemption tolerance with 알고리즘 정확성 보장
- Hardware error robustness
- RL/OPD rollout 안정성 ↑

## 5단계: §5.2.4 Scaling RL Framework for Million-Token Context

### Motivation

V4 는 1M context 학습 가능 → RL/OPD 도 1M context rollout 으로 확장.

### 도전
- 1M token rollout 의 raw data: 수십 GB / sample
- 표준 data loader: in-memory 적재 → **메모리 폭발**
- Single rollout 이 GPU 메모리 한계 초과 가능

### V4 의 해결 — 데이터 형식 분리

**(a) Light metadata vs Heavy per-token fields**
- Metadata: prompt info, sample index 등 (작음)
- Per-token: token ID, log-prob, hidden state 등 (큼)

**(b) Metadata-only global pre-load**
- 전체 rollout metadata 만 미리 load
- Global shuffling 과 packing layout 계산 가능

**(c) Heavy fields lazy load via shared-memory**
- Per-token field 는 **shared-memory data loader**
- Intra-node redundancy 제거
- Mini-batch 사용 후 즉시 release → CPU/GPU 메모리 압박 ↓

**(d) Dynamic mini-batch sizing**
- Workload 에 따라 on-device mini-batch 수 동적 결정
- Computational throughput vs I/O overlap 의 trade-off 자동 조절

→ Million-token RL/OPD 가 가능해짐.

## 6단계: §5.2.5 Sandbox Infrastructure for Agentic AI — DSec

### Motivation

V4 의 agent 능력을 학습하려면 **다양한 실행 환경** 필요:
- 단순 function call (Python interpreter 등)
- Container (Docker compose, software pipeline)
- microVM (security-sensitive isolation)
- fullVM (arbitrary OS)

### V4 의 해결 — DeepSeek Elastic Compute (DSec)

**구성**:
- API gateway (Apiserver, Rust)
- Per-host agent (Edge, Rust)
- Cluster monitor (Watcher, Rust)
- Custom RPC protocol
- 3FS distributed filesystem 위에서 horizontally scale

### 4 가지 execution substrates 통일 인터페이스

```python
libdsec.exec(...)   # 같은 API 로
   ↓
   ├─ Function Call: pre-warmed container pool (cold-start 0)
   ├─ Container: EROFS [P56] on-demand image loading
   ├─ microVM: Firecracker [P57] (VM-level isolation, security-sensitive)
   └─ fullVM: QEMU [P58] (arbitrary OS)
```

### Fast Image Loading

- **Container 의 base image**: 3FS-backed readonly EROFS layers, mount lowerdirs
- **microVM 의 disk**: overlaybd format
  - Read-only base on 3FS (cross-instance sharing)
  - Writes go to local copy-on-write layer
  - Snapshots chainable → versioning + msec-level resumption

### Density Optimizations

- **수십만 sandbox per cluster**:
  - Page cache duplication 완화 + memory reclamation
  - Container runtime 의 spinlock 제거 → per-sandbox CPU overhead ↓

### Trajectory Logging + Preemption-Safe Resumption

- Globally-ordered trajectory log per sandbox
- 3 가지 활용:
  1. **Client fast-forwarding**: preemption 후 cached results 로 빠른 복구
  2. **Fine-grained provenance**: state change 추적 가능
  3. **Deterministic replay**: 어떤 historical session 도 정확히 재현

### Why this matters

- Agent post-training (코드 실행, tool use, multi-step task 등) 이 가능
- DSec 없이는 §5.4.4 의 R&D coding agent benchmark (~67% 통과) 만들 수 없음

## 7단계: 종합 — 인프라가 곧 capability

### V4 의 메시지

§5.2 가 보여주는 패턴:
- **OPD 라는 새 pipeline** 은 §5.1 에서 design
- 그러나 **infrastructure 가 받쳐주지 않으면 paper 에만 머무름**
- §5.2 의 디테일이 **OPD 가 production-ready 가 되는 결정타**

### 다른 OSS 와의 차이
- 많은 OSS 가 OPD/distillation 시도하지만 **trillion-scale teacher × 10+ teachers × 1M context** 까지 확장한 곳은 거의 없음
- V4 의 **centralized teacher storage + hidden state caching + teacher-indexed ordering** 이 세 디자인이 핵심

## 정리 — §5.2 한눈에 보기

| 도전 | V4 의 해결 | Why |
|---|---|---|
| FP4 in post-training | rollout/inference 직접 FP4, training simulated dequant | 가속 + 메모리 |
| 10+ teacher weight 메모리 | centralized distributed storage + on-demand load | trillion-scale 동시 적재 불가 |
| Full-vocab logit 폭발 | last hidden cache + prediction head recompute | 128K vocab → hidden 7K 차원 |
| Teacher head GPU memory | teacher-indexed sample ordering | mini-batch 당 1 head |
| KL 계산 비용 | TileLang specialized kernel | naive PyTorch 비효율 |
| Preemption + length bias | **token-granular WAL** | algorithmic correctness |
| 1M context RL data | metadata 분리 + shared-memory loader | 메모리 폭발 회피 |
| Agentic execution | **DSec** (4 substrates 통일 SDK) | 다양한 task 환경 |

**핵심 통찰**:
1. **OPD 의 success 는 §5.2 인프라에 달림** — design 만으로는 불충분
2. **Centralized teacher storage + last hidden caching** 이 multi-teacher OPD 의 결정타
3. **Token-granular WAL** 이 RL rollout 의 algorithmic correctness 보장 — 단순 retry 는 length bias 발생
4. **DSec** 은 단순 sandbox 가 아닌 production-grade 4-substrate 시스템 — agent capability 의 base
5. §5.1 architecture 와 §5.2 system 은 **§2-§3 와 같이 동전의 양면**
