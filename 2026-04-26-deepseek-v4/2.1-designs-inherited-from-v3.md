# §2.1 Designs Inherited from DeepSeek-V3 — 차근차근

V4가 "유지한 것"과 "조정한 것"을 이해하려면 먼저 **DeepSeek 시리즈가 V2부터 다듬어온 MoE 설계**를 알아야 한다. 한 단계씩 짚는다.

---

## 1단계: MoE의 기본 개념 (background)

**Mixture-of-Experts(MoE)** 는 모든 입력 토큰에 대해 모든 파라미터를 쓰는 dense 모델 대신, **여러 "expert" FFN 중 일부만 선택해서 사용**하는 구조다.

```
  입력 x ─→ Router ─→ "expert 3, expert 7 활성화"
                   ─→ FFN_3(x), FFN_7(x) 만 계산
                   ─→ weighted sum
```

- **장점**: 총 파라미터는 1.6T이지만 토큰당 49B만 계산 → "trillion급 모델을 100B급 cost로"
- **문제 1 — load balance**: Router가 일부 expert만 편애하면 나머지는 죽은 weight
- **문제 2 — expert specialization**: expert가 너무 적거나 너무 크면 역할 분화가 안 됨

이 두 문제를 해결하는 방식이 MoE 연구의 핵심이고, DeepSeek은 **DeepSeekMoE 논문(Dai et al. 2024, [P2])** 에서 자기만의 답을 제시했다.

---

## 2단계: DeepSeekMoE의 두 기둥 (V2부터 V3까지 유지)

### (a) Fine-grained expert segmentation

- **기존 (Switch Transformer 등)**: 큰 expert FFN을 N개 만들고 그 중 K개 활성
- **DeepSeekMoE**: 같은 파라미터 예산으로 **각 expert의 hidden dim을 1/m로 줄여 mN개로 쪼갬**, 활성 수도 mK로 늘림
- 효과: **expert 조합의 경우의 수 폭증** → 더 정밀한 specialization

예: V3는 1 shared + **256 routed experts**, **8개 활성** (V4-Pro는 384/6, V4-Flash는 256/6).

### (b) Shared expert isolation

- 일부 expert를 "shared"로 지정해 **모든 토큰이 항상 통과**
- 역할: "공통 지식" 캡처 → routed expert들은 specialization에 집중

DeepSeekMoE 논문에 따르면 이 두 전략으로 **2B MoE가 GShard 2.9B와 동급, 16B가 LLaMA2 7B와 동급(40% 연산)** 을 달성했고, V2/V3가 그대로 계승했다 [P2, P3].

---

## 3단계: Auxiliary-Loss-Free Load Balancing (V3에서 도입, V4 유지)

### 기존 방식의 문제 — Auxiliary loss 의 부작용

전통적 load balancing은 **보조 손실**을 훈련 손실에 더한다:

```
L_total = L_LM + α · L_balance
```

`L_balance`는 expert 사용량의 분산 등을 페널티화. 문제:
1. **언어모델링 loss와 다른 방향의 gradient**를 추가 → 모델 성능 저하
2. **α 조정이 까다로움**: 너무 크면 성능↓, 너무 작으면 imbalance

### DeepSeek-V3의 해법 — Bias 직접 조정

논문 *"Auxiliary-Loss-Free Load Balancing Strategy for MoE"* (Wang et al. 2024, [P4]):

```
affinity_score(expert_i) = Sigmoid(x · W_i) + b_i
                                              └─ 학습 안 되는 "bias 항"
```

- `b_i` 는 **gradient로 업데이트되지 않고**, batch마다 **사용량 관찰 후 직접 조정**
- expert i가 평균보다 많이 쓰이면 `b_i` 감소, 적게 쓰이면 증가
- DeepSeek-V3는 처음 14.3T 토큰 동안 update speed γ=0.001, 마지막 500B 토큰은 γ=0 [P4]

→ **gradient를 오염시키지 않으면서 균형 달성**. 실험상 더 좋은 성능 + 더 좋은 balance 둘 다 [P4].

## 4단계: Hash Routing — V4의 새 추가

### 기존 문제

**dense FFN을 초기 몇 레이어에 두는 관행**:
- V3까지 모든 MoE 모델이 첫 1~3 레이어를 dense FFN으로 두는 관행
- 이유: **초기 레이어는 학습 초반 routing이 불안정** → expert 선택이 망가지면 모델 전체가 망가짐
- 비용: 그 레이어들에서 **MoE의 효율성 이득 포기**

### Hash Layers (Roller et al. 2021, [P5])

**Routing을 학습 안 시키고 token ID로 hash function 적용**:

```
expert_index = hash(token_id) % N
```

- 학습 파라미터 없음, balance loss 불필요, balance 알고리즘 불필요
- Roller et al. 결과: **Switch Transformer / BASE Layer와 동급 또는 우수** [P5]
- 단점: token ID에만 의존하므로 **context-aware routing 불가** → expert specialization은 학습형보다 약함

### V4의 절충

> "we replace the dense FFN layers in the initial several Transformer blocks with **MoE layers that employ Hash routing** (Roller et al., 2021)."

- 초기 3 레이어: Hash-routed MoE (학습 불필요 = 안정성)
- 이후 모든 레이어: 표준 학습형 MoE (DeepSeekMoE)

→ "**dense의 안정성 + MoE의 효율성**" 절충. 초기 학습이 불안정한 시기를 hash로 건너뛰고, 나머지는 정상 routing.

## 5단계: V4의 그 외 작은 조정들

### (a) Sigmoid → Sqrt(Softplus)

**왜 affinity 함수를 바꿨나?**

- **Sigmoid 문제**: 큰 입력에서 saturate → gradient ≈ 0 → 우세한 expert가 점점 더 우세, 다양성 ↓
- **Softplus**: `softplus(x) = log(1 + e^x)` — 큰 양수에서 거의 linear, gradient 살아있음
- **Sqrt(Softplus)**: `√(log(1+e^x))` — softplus의 빠른 증가를 완만화하여 gating dynamics 안정

→ saturation 회피하면서 score scale도 적절히 제어.

### (b) Sequence-wise balance loss 추가

**Auxiliary-loss-free의 한계**:
- bias 조정은 **batch 단위 평균 사용량** 기반
- batch 안에서 평균은 맞아도 **단일 sequence 내부에서는 한쪽 expert에 쏠릴 수 있음**
- long-context (1M) 에서는 sequence 자체가 매우 길어 이 편향이 심각

**V4의 해법**: 매우 작은 weight (`0.0001`)의 sequence-wise balance loss를 보조로 추가
- 보조 loss의 부작용을 최소화하면서 sequence 내부 균형만 보정

### (c) 라우팅 노드 제한 제거

**V3까지**: 한 토큰이 활성화하는 expert가 분산된 노드 수에 상한을 둠 (통신 비용 제어)

**V4**: 제한 제거 + parallelism 전략 재설계
- 이유: V3의 제한이 large MoE EP scaling 효율 저해
- 새 통신 패턴(MegaMoE, §3.1) 으로 노드 분산 비용을 흡수

### (d) MTP (Multi-Token Prediction) 그대로 유지

- V3에서 검증된 기법 [P3]: 다음 1+N 토큰 동시 예측
- 학습 가속 + reasoning 능력 향상
- "검증된 건 건드리지 말자" 원칙으로 변경 없음

## 정리 — §2.1 한눈에 보기

| 구성 요소 | V3 | V4 변경 | 변경 동기 |
|---|---|---|---|
| Fine-grained expert | ✓ (256/8) | ✓ (256/6 또는 384/6) | scale up |
| Shared expert | ✓ (1개) | ✓ 동일 | 검증됨 |
| Affinity 함수 | Sigmoid | **Sqrt(Softplus)** | saturation 회피 |
| Load balance | aux-loss-free [P4] | **+ seq-wise loss(0.0001)** | 1M context 단일 시퀀스 균형 |
| 노드 제한 | 있음 | **제거** | EP scaling 효율 |
| 초기 레이어 | dense FFN | **Hash-routed MoE** [P5] | 안정성 + 효율 동시 확보 |
| MTP | ✓ | ✓ 동일 | 검증됨 |

**핵심 메시지**: §2.1은 "혁신"이 아니라 **V3 검증된 기반 위의 점진적 안정화·효율화**. Hash routing 도입이 가장 의미 있는 변경 (dense FFN 관행 깨기).
